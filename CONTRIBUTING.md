The Programmer's Learning Machine (PLM) is a free cross-platform programming exerciser. It lets you explore various concepts of
programming through interactive challenges in differing micro-worlds, that you can solve in either Java, Python, Scala or C. The
design rational is given in the following paper: [The Programmer's Learning Machine: A Teaching System To Learn
Programming](https://hal.inria.fr/hal-01243646). On this page, you will find the following sections:

* [Overall architecture](#architecture) and concepts, to help the onboarding of prospective contributors
* [How to translate the project](#translating-the-plm)
* [How to add new lessons, exercises and universes](#extending-the-plm)
* [Maintainer's notes](#maintainers-note): how to merge in new translation and how to release a new version of the PLM.

# Architecture

## Core concepts

- **World + Entity**: a `World` (`plm.universe.World`) is the simulated environment encoding a pedagogical problem situation.
  This is a micro-world instance. It contains one or more `Entity` objects, which are the actors that execute the student's code
  (or the teacher's correction code) against the world's primitives. 
- **Universe**: a micro-world *kind*, i.e. a family of worlds/entities sharing a theme and a set of primitives (e.g. "a buggle
  can walk, paint, pick up objects" or "a turtle draws on the ground as it moves"). Universes are found in `src/plm/universe`
  for the generic ones and in `src/lessons/*/universe` for the ones specifically tailored for a given lesson. See the
  [pedagogical documentation](PEDAGOGY.md#universes) for more information.

- **Exercise**: the unit of work a student solves (`plm.core.model.lesson.Exercise`). An `Exercise` is a programming challenge
  aiming at teaching or exercising a given concept. A given exercise uses exactly **one** universe. An exercise comes with a set
  of worlds and entities that act as **test cases** for the student code. Each provided world must pass for the exercise to be
  validated. This is thus comparable to parametrized unit tests: Adding another world instance to an exercise, without touching
  the student-facing code, is the standard way to catch a wider range of incorrect solutions.
- **Lesson**: a `Lesson` (e.g. `welcome`, `sort`, `recursion`) groups `Exercise`s in a pedagogical sequence. Each of them
  constitute a progressive set of challenges taking the users through their learning path. Again, see the [pedagogical
  documentation](PEDAGOGY.md#learning-material) for details.
  
- **Templating entity**: for each exercise/language pair, a source file (e.g. `MoriaEntity.java`, `MoriaEntity.py`,
  `MoriaEntity.scala`, `MoriaEntity.c`) contains both the teacher's reference correction, the template shown to the student and
  the code harness to execute the student code. See [Code templating](#code-templating-preparing-the-source-to-compile) below
  for the file layout.

## How an exercise executes: the 30,000 feet overview

* **Exercise setup**: Each exercise comes with a `setup()` method that creates the pedagogical settings and populates the
  microworlds with entities. The exercise owns **three parallel sets of worlds**:
  - `initialWorld`: the starting state, as built by `setup()`.
  - `answerWorld`: the target state, produced by either loading a cached solution from the disk, or by running the teacher's
    correction code on the corresponding `initialWorld`. See [World I/O and the answer cache](#world-io-and-the-answer-cache) below.
  - `currentWorld`: the current state while executing the student's code, initially equal to `initialWorld`. If the
    `currentWorld` becomes semantically equal to `answerWorld` after executing the student code, the exercise is passed.

The entry point of the whole execution is `Exercise.compileRunCheck()`. It chains the steps below, from the reset to the check, and
is called by `LessonRunner` when the student clicks "Run" (compiling the student's code) and by the integration tests (compiling the
correction entity). It returns the `RunOutcome` of the execution. A compilation error, or a refusal by `verifySource()`, is
returned too, as an outcome of kind `COMPILE` holding the message: the exceptions of the compilers do not go past this method.
Nothing is stored in the `Exercise`: the outcome is passed along to the dialogs and to the progress trackers.

Here are the steps of the exercise execution:
* **Reset**: `currentWorld` is reset from `initialWorld` for each world instance.
* **Templating**: A compilable source code is generated by extracting the execution harness of the correction entity, and
  replacing the body of that entity with the student's code (i.e., the current editor's content). See the section on [templating](#code-templating-preparing-the-source-to-compile)
  below.
* **Compile**: The starting point is `ProgrammingLanguage.compileExo()`.
  - The code is then compiled to an external executable/jar if needed. Java/Scala compile in-process to avoid the startup time of an
    external JVM, C uses an external compiler, and Python is checked by `python3 -m py_compile`.
  - `compileExo()` returns a textual reference to the result (the path to a jar, a binary, etc), which the caller then passes
    down as-is to `runEntity()`'s `executable` parameter below.
* **Source verification**: `Exercise.compileRunCheck()` then calls `Exercise.verifySource()` with the editor's content, for the
  student's code only (not for the correction). Exercises override it to refuse a code that compiles but misses the point (see
  "API gating" below).
* **Remote execution**: `World.runEntities()` spawns one thread per entity and calls `ProgrammingLanguage.runEntity()`: that
  method binds a TCP socket on 127.0.0.1, starts the student code as an external process, and relays primitive calls over that
  socket to `plm.universe.CommandExecutor`. These primitives allow the student code to interact with the microworld that is
  located in the PLM process. This is transparent to both the student and the exercise authors, unless the exercise gates its
  API (see [API gating](#api-gating-restricting-or-adapting-the-primitives) below).
* **Check**: when all entities are terminated, `Exercise.check(result)` compares each `currentWorld` to its `answerWorld` via
  `World.winning()`, and fills the `RunOutcome` that `compileRunCheck()` then returns. On mismatch, `World.diffTo()` produces a
  human-readable diff shown to the student. All the universes but Lander use a structural equality between currentWorld and
  answerWorld to compute whether it's winning. Instead, Lander checks whether the lunar lander reached a pad or crashed. In
  creative mode (a flag of `Game`), the worlds are neither reset nor checked.
* **Session saving**: each student attempt is saved in a local git repository along with the exercise outcome (compilation
  error, failed objective or passed). The goal is to enable learning analytics if the student allowed the export of her
  anonymized data to an online repository. The progress trackers get the outcome with `executed(exo, outcome)`.

* **Lightbot specificities**: this brain teaser can only be solved using the graphical block-list rather than a real programming
     language. Thus, `run()` *interprets* a student-authored program and there is no templating nor remote execution. The
     program is stored in the `SessionDB` as any other editor content: one line per function (main, then the two others), one
     character per instruction. `LightBotEditorPanel` rewrites it at each change of a chooser, and `LightBotEntity` parses it
     again when it runs.

* **Dealing with infinite loops in student code**. The "Stop" action calls `LessonRunner.stopAll()`, which cooperatively
  `Thread.interrupt()`s each per-entity runner thread. Since student code is an external process, interrupting the runner thread
  only unblocks it from `Process.waitFor()`; `RemoteExecutionLang.runEntity()` catches that `InterruptedException` and calls
  `destroyForcibly()` on the child process before returning, so a stopped infinite loop does not leave any orphaned process
  behind. This mechanism is not a hard sandbox either: the process is killed, but nothing prevents it from spawning its own
  children or from being heavy enough to matter for the second or so it takes to die.

## Code templating (preparing the source to compile)

This section is about how the single `XxxEntity.<ext>` file described in [Adding a new exercise](#adding-a-new-exercise) below (which mixes the
teacher's solution and the student-facing template) becomes two different compilable programs: one for the CORRECTION which is
used to compute the demo and the `answerWorld`, and one for the student's current editor content when the "Run" button is hit in
the GUI. This process can be decomposed as follows:

- When the lesson is loaded, `ExerciseTemplated.setup()` only checks which languages have an entity file (`FileUtils.exists()`)
  but the files are not parsed nor loaded in memory at this stage since we almost never need to parse all entities in all
  language for a given PLM usage session (the exception is the entity that `computeAnswer()` compiles and executes, i.e. the
  exercises with a missing or broken cache on disk, and the ones with a randomized world). `LightBotExercise` has no entity
  file: it overrides `setup()` and creates a plain `SourceFile`, whose editor content is the textual representation of the
  student's program (see `LightBotProgram`).
- When needed by `ProgrammingLanguage.compileExo()`, the entity content is parsed (split into parts), and a `SourceFile` is
  created to store the result of this parsing. This step (detailed below) is language agnostic: it applies exactly the same for
  all entities of all languages.
- When the "Run" button is hit, a compilable file content is derived from the current content of the editor and along with the
  `SourceFile` that was previously parsed. This happens for each new exercise compilation, and also to compile the correction
  entity that computes the `answerWorld`.

### Entity content parsing: `EntityTemplateParser.parse()` (language agnostic code -- cached result)

The entity file is read and parsed the first time `Exercise.getSourceFilesList(lang)` is called for that language (see
`loadSourceFiles()` and `newSourceFromFile()`). The result is cached as a `SourceFile` in `Exercise.sourceFiles`.
`Exercise.getLoadedSourceFiles(lang)` returns what is already loaded without parsing anything: session saving and
`Game.revertExo()` use it.

`split()` cuts the file into segments, driven by marker comments. Markers are matched anywhere in a line, expected alone on it,
and removed from the segments:
- `BEGIN/END TEMPLATE`: the code initially shown to the student in the editor (at most one).
- `BEGIN/END SOLUTION`: code kept for the correction but hidden from the student. With a `TEMPLATE`, there can be any number of
  `SOLUTION`s, before, inside or after it. Without a `TEMPLATE`, there is exactly one `SOLUTION`, and it plays the role of the
  templated region: the editor is initially empty in this case. An entity without any `SOLUTION` is rejected as a likely
  mistake: if the template is meant to be the answer already, say so with an empty `SOLUTION` section.
- `BEGIN/END IMPORT`: extra imports, kept out of the template.
- `BEGIN/END REMOTE` (optional): narrows what counts as head and tail. Everything before `BEGIN REMOTE` and after `END REMOTE`
  is dropped, which lets Java/Scala leave out their own package/class declaration (their wrapper provides it). It must fully
  enclose the templated region, and any `SOLUTION` out of the template region must be within the remote region.

Any invalid markup throws a RuntimeException (unmatched or nested markers, several `TEMPLATE`s, a `SOLUTION` straddling another
marker, ...).

What lies within REMOTE but outside the templated region is the `head` and the `tail`. The tail starts with a `\n` so that
Python sees it as a new block, even if the student left indented blank lines at the end of the body. 

The resulting `SourceFile` holds:
- `remote`: the name of the `RemoteXxx` universe, guessed by `guessRemote()` from the entity file content.
- `imports`: the content of the `IMPORT` sections.
- `bodyIndent`: the indentation shared by the whole templated region. Python uses it to reindent the editor's content before
  injecting it in the generated source code.
- `student`: an `EntityFileSegments(pre, body, post)` record, where:
   - `student.pre` is the head and `student.post` the tail without any `SOLUTION` section.
   - `student.body` is the initial editor content: the lines between `BEGIN TEMPLATE` and `END TEMPLATE` without the `SOLUTION`
      sections, or an an empty string when there is no TEMPLATE marker (the SOLUTION is then the templated region). It is
      dedented by `bodyIndent`. Leading tabs are expanded in Python, with tab stops every 8 columns, and replaced by 4 spaces in
      the other languages.
- `correction`: same record, to generate a correction entity, but `correction.pre` and `correction.post` keep the `SOLUTION`
  sections of head and tail. `correction.body` is the raw span (markers included) from `BEGIN TEMPLATE` to `END TEMPLATE`, or
  from `BEGIN SOLUTION` to `END SOLUTION` when no template is given.

A SourceFile is immutable after its creation. There is one per exercise and language, and its editor tab is labeled with the
exercise's `tabName`, which must be an identifier since it names the files given to the compilers (the generated class is always
called `Entity`, whatever this name is). What the student wrote for a given exercise and language is stored in the `SessionDB` (see
"Saving the student's work" below), and accessed through `Exercise.getEditorContent()` and `Exercise.setEditorContent()`. The
initial content of the editor content is the `student.body` field, publicly available from `SourceFile.getInitialBody()`.

An `Exercise` is not constant and could not be shared in memory between different users of the same PLM process. It still
holds mutable state: its `currentWorld`, `initialWorld` and `answerWorld` vectors (the current worlds change at each run, the
initial ones may be randomized, and the answer ones are computed lazily and cached on disk), the `sourceFiles` cache that is
filled on demand, and its `i18n` that depends on the locale of the `Game` at the creation. The lesson also remembers its current
exercise (`Lesson.currentExercise`).

### Building a compilable source (language-specific code in `compileExo()`, not cached)

Each `compileExo()` gets the `EntityFileSegments` using `Exercise.getSegments(lang, sourceFile, whatToCompile)`, with whatToCompile
being either `StudentOrCorrection.CORRECTION` or `STUDENT`. It relies on `SourceFile.getCorrectionSegments()`, or on
`SourceFile.getStudentSegments(body)` with the current editor content. It then concatenates `pre`, the body (either the editor's content or the
teacher's correction) and `post` with what its language needs:
- Java/Scala wrap them in their own class/object boilerplate: `package`, their imports (all on a single line, so that the line
  numbers of the generated code do not depend on how many there are), `class Entity {`, then `pre`, the body, `post` and a
  closing brace.
- Python only prepends its own imports, followed by the `IMPORT` sections of the entity, with no further boilerplate. As
  indentation matters in Python, it indents the student's code by `bodyIndent` spaces (after removing its own common
  indentation) before concatenating it. The tabs found in the leading white-space of the whole source (entity and student) are
  then expanded as well, so that tabs and spaces never get mixed up.
- C starts with the `IMPORT` sections of the entity, then `pre`, a `#line` preprocessor directive and the body, so that compiler
  errors point at the entity's own file.

Each language does this concatenation inline in its own `compileExo()`, to keep a single linear flow instead of jumping to a
handful of one-off helper lines elsewhere:
  - Java/Scala/Python first compute `offset` via `JvmTemplatedLang.countLinesBeforeBody()`: it is the number of lines of the
    generated source before the body's own first line. It is used to fix (shift) the location of compilation errors so that they
    point to the code written by the student. Diagnostics located before the body are left untouched, and so are all of them
    when debugging is enabled, to keep the path of the generated file. Java gets them from javac's `DiagnosticCollector`, Scala
    from dotc's `SimpleReporter`. All three languages also subtract this number from the `Entity.java:N`, `Entity.scala:N` and
    `Entity.py", line N` locations found in the stack traces that the student process writes on its stderr, through the
    `RemoteExecutionLang.shiftLocations()` hook (`JvmTemplatedLang` keeps the offset of each compiled jar in `lineShifts`).
    Locations before the body (and all of them when debugging is enabled) are left untouched in both compilation errors and
    stack traces.
    - C does not need to compute the offset, as a `#line` preprocessor directive already fixes the error location.
  - Java/Scala/Python add a trailing space and newline after the body, so that a body ending right before the closing brace
    still parses.
  - Python fixes the indentation: the tabs of the leading whitespace of the editor's content are expanded (tab stops every 8
    columns, as python reads them, whatever the editor stored) and the body is reindented to fit its position in the source.
  - non-breaking spaces are stripped.
- The resulting source is written to a per-compile directory on disk which name is unique, so unrelated concurrent compiles
  never collide. A `Main` containing the execution harness is also generated in this directory, and both files are compiled.
- The glue that does not depend on the exercise (`Remote`, `RemoteXxx`, `ValueSerializer`, `Point`, `RecList`...) is built once
  and shared by all compilations:
  - Java/Scala: `CodeCreation` (run by maven at `process-classes` stage) generates the `RemoteXxx` sources, then compiles them
    in-process with the helper sources into `plm-entities-java.jar` and `plm-entities-scala.jar`. The staged sources are kept in
    `target/plm-entities/` for debugging but excluded from PLM.jar by a filter of the shade plugin. The jars are resources of
    PLM.jar, deployed to `/tmp/plm` upon compilation and put on the classpath of both the compilation and the run.
  - Python: the modules are deployed in `/tmp/plm/python-entities`, which is prepended to the `PYTHONPATH` of the run. Python caches
    their bytecode by itself.
  - C: `LangC.ensureCachedObject()` compiles each file once to an object cached in `/tmp/plm/C/objects`, which is linked with each
    exercise.

## Remoting: how the student's entity talks to the PLM

The student's code runs in its own process (`java -cp ... generated.Main`, `python3 Main.py`, or the C executable), while the
world, its entities and the UI live in the PLM process. The student's code only manipulates a stub: each primitive call is
forwarded to the real `plm.universe.Entity` of the PLM, which does the actual work on the `currentWorld`.

- **Transport**: `RemoteExecutionLang.runEntity()` binds a TCP socket on a free port of `127.0.0.1`, and starts the student
  process with that port as its first argument (`args[0]`, `sys.argv[1]`, `argv[1]`). Both sides must stick to the literal IPv4
  loopback address: binding any other interface (or `0.0.0.0`) would expose the protocol to other hosts and trigger the firewall
  prompts of Windows and macOS, which do not filter the loopback; `localhost` may resolve to `::1` on one side only. UNIX domain
  sockets are not an option, as Python has no `AF_UNIX` on Windows. Both sides set `TCP_NODELAY`, since each command is a short
  request awaiting its answer. The generated `Main` starts by calling `connect()` from the language's `Remote` file. If nothing
  connects within 10 seconds, the process is killed and its stdout/stderr become the error message shown to the student. Once
  connected, both sides exchange UTF-8 text, one message per line.
- **Student-side glue**: it is made of `Remote` (the connection, `sendCommand()` and the `getAnswerXxx()` readers), a
  `ValueSerializer`, and one generated `RemoteXxx` per universe, with one function per primitive of that universe. They are the
  files that the templating does not compile with the exercise (see above for how they are built and shared). Every language has
  its own implementation of this glue in `lib/resources/langages/` (except Scala, which uses the Java `Remote`), plus the
  generator in its `ExternalPrimitiveLanguage`. 
  
  A universe may complete its glue with hand-written code, in files named after the glue and the extension of the generated file
  (e.g. `RemoteConsGlue.py`, or `RemotePosixGlue.h` and `RemotePosixGlue.c` in C), next to the sources of its entity:
  `CodeCreation` appends them verbatim to the generated files. As they are fragments, maven does not compile the
  `Remote*Glue.java`. With `@Glue(value = "...", wrapped = true)`, this hand-written part wraps the generated functions to offer
  a more idiomatic API than the primitives (e.g. the C system calls with their buffers and structures). Only the C generator
  supports it for now: its generated functions become static and named `plm_remote_xxx`, and are not declared in the header.
- **Primitives**: the primitives of a universe are the methods annotated with `@Primitive` in the interfaces extending
  `EntityPrimitivesBase` (e.g. `SimpleEntityPrimitives`), which the entity implements. `PrimitiveRegistration` finds them by
  reflection. At build time, `CodeCreation` generates the `RemoteXxx` glue of every language from them. A primitive is identified
  by its method name, which must be unique: primitives cannot be overloaded, which `PrimitiveRegistration` checks.
  The annotation carries the English documentation of the primitive and the title of its group, e.g. `@Primitive(value = "Turns a
  quarter to the left.", group = "Moving")`. `PrimitivePot` extracts these texts and the names of the documented primitives into
  `l10n/engine/plm.pot`, so that they get translated on weblate.
  The groups are ordered by `@PrimitiveGroups` on the primitives interface (or on the entity). `World.getAbout()` replaces the
  `[!primitives/]` placeholder of the world's html by a table of the documented primitives of its first entity, in the current
  programming language (`ExternalPrimitiveLanguage.signature()`). The primitives forbidden by the exercise are not shown.
  Likewise, `[!colors/]` stands for the table of the named colors of `ColorMapper`: their name in the code, a sample, and their
  translated name used in the messages to the students.
- **Translated primitives**: translators may give a localized name to each documented primitive (entries of context `primitive`
  in `l10n/engine/*.po`). `CodeCreation` adds the aliases of every locale to the glue (`PrimitiveAliases`), so that the code of
  a student keeps working when switching the human language. An alias sends the canonical name of its primitive
  (`PrimitiveMethod.command()`): the rest of the PLM, API gating included, only knows the canonical names. The build fails if a
  translated name is not a valid identifier in every language (accented letters are fine, but not decomposed ones) or designates
  two primitives of the same glue. The Scala, Python and C corrections of `InstructionsDrawG` call a few aliases, so that
  `ExoTest*Lang` checks them in the glue. The Java correction cannot: the entity file is also compiled by maven as a class of
  the PLM (extending SimpleBuggle), which only has the English names; the aliases only exist in the generated glue.
- **Commands**: calling a primitive in the student's code sends `<name> <serialized args>`, e.g. `setObjectif [1:b1]`
  for `setObjectif(true)`. The arguments always are serialized as one array. The parsing relies on the first space of the
  line, since the serialized arguments may contain some (in strings). If the primitive returns something, the glue
  then blocks on `getAnswerXxx()` until the PLM answers with one line holding the serialized result. The `Answer` enum lists
  the types that a primitive can return, and each generator maps them to the function of its glue. Primitives that return
  nothing get no answer: the student's code does not wait for the PLM.
- **Serialization**: `ValueSerializer` writes each value with a type tag: `i` for ints, `f` for doubles, `b0`/`b1` for booleans,
  `c` for chars, `C` for colors (ARGB int), `Px:y` for points, a quoted string with `\\`, `\"`, `\n` and `\r` escapes (the
  protocol sends one value per line), `x` followed by the hexadecimal digits for byte arrays (binary data, that may contain any
  byte), and `Z` for null.
  Arrays are `[n:v1:v2...]`, prefixed by the tag of their elements, and nest for multi-dimensional ones. Enums travel as their
  ordinal. It exists in Java (`plm.core.ValueSerializer`, which is compiled in the glue jarfile), Python (`ValueSerializer.py`)
  and C (`value_serializer.c`): the three must be kept in sync, which `ValueSerializerInteropTest` checks.
- **PLM side**: the `commandReader` thread of `runEntity()` reads the commands and passes each of them to
  `CommandExecutor.command()`. It finds the primitive by name, deserializes the arguments, converts the enums from their
  ordinals (and, for Python, the typed values to the strings that the primitive expects), calls the Java method of the real
  entity by reflection, and writes the serialized result back if the primitive has one. A primitive that the entity forbids is
  refused before anything else (see [API gating](#api-gating-restricting-or-adapting-the-primitives) below). An exception in the
  primitive is reported to the student with the command that triggered it, except an `ExplainedException`, whose message explains
  the error to the student and is reported as is: a `PrimitiveRefusedException` when gating a primitive on purpose, or an error of
  the program detected by the world (such as a deadlock in the POSIX universe). A command that cannot be parsed fails the run and kills
  the process.
- **Animation**: the primitives call `Entity.stepUI()`, which sleeps for the delay of the world, or waits for the next step in
  step mode. As this happens in the `commandReader` thread, it slows down the display but not the computations of the student
  code, which only waits when it needs an answer.
- **Concurrency**: the worlds of an exercise run in parallel, but the entities of a world share it. `CommandExecutor` thus
  locks the world of the entity during each command, and `World.awaitStep()` releases that lock while the entity waits for its
  animation. The entities of an animated world (run by `World.runEntities()`) also move together: they start together, and
  each of them waits for the others after each step, using a `Phaser`. That's why they run on threads of their own: the
  bounded pool of `Game` is only used to compute the expected worlds when loading a lesson, which are not animated.
- **End of the run**: `runEntity()` also reads the stdout and stderr of the process, echoes them to the PLM console and keeps
  them (stderr goes through `shiftLocations()`, see above). After the process ends, it joins its threads, lets the language
  inspect what the process left behind (`onProcessFinished()`, used by C for the address sanitizer report), and removes the
  socket. A non-zero exit code is reported as an execution error.

## Saving the student's work

The student's progression is automatically persisted on disk, and optionally in the cloud if the student opts-in. Cloud
persistence is based on a public git repository shared between all users. The users identity is not stored in the public git,
but only their `userUUID`. No security is provided whatsoever, so anyone could possibly hijack the session of another user to
pass exercises in their (anonymous) name, but why would someone bother doing so? Saving the data in a public but anonymized git
makes it possible to explore the learning analytics, to assess and improve the pedagogical content and to understand the
learning paths of the users.

Persisting the student's progression on disk and in the cloud relies on three main concepts:

- **Session DB:** The session is the in-memory database of the student's progress. It never touches the disk nor the network.
- **Session kits:** The kits save and restore the SessionDB. The `GitSessionKit` reads the session from a local git repository
  at startup. A session can also be exported to a zip file and imported from it (see `GitTracker.exportSession()`).
- **Progress trackers:** The trackers react to the events such as a run attempt or switching exercises. The main tracker is
  `GitTracker`, that commit the data to a local git repository that is optionally synchronized online. Other trackers are
  planned, e.g. to give the teacher an overview of the class progress and tell her who needs help, or a *king of hill* mode
  where students can compare their progress to the one of their friends.

### Session DB

The `SessionDB` (`plm.core.model.session`, one instance per PLM, `Game.studentWork`) is the in-memory state of the student's
progress, which the UI queries all the time (the progress icons of `ResourcesCache`, the bars of `ChooseLessonDialog`). It never
touches the disk nor the network: the session kits fill it in while the progress trackers persist it automatically on disk. It
holds three things:
- The *editor contents*: what the student wrote, by exercise and language. It is accessed with `setBody()` and `getBody()`,
  through `Exercise.getEditorContent()` and `Exercise.setEditorContent()`. A body is absent until the student changes the
  initial content, and `Exercise.getEditorContent()` uses `SourceFile.getInitialBody()` when the body is absent in the DB. The
  editors register with `setBodyListener()` to be told of every change, whoever made it. `removeBodies()` forgets everything the
  student wrote for an exercise: this is the revert action. The bodies are concurrent maps because the run thread reads them
  while the Swing event thread writes them.
- The *pass state* of each exercise in each language (`setPassed()`/`getPassed()`, false for an exercise never seen).
  `GitSessionKit.loadLesson()` fills it from the `.DONE` files when a lesson loads, `LessonRunner` sets it when the exercise
  passes, and the revert action and `Game.clearSession()` set it back to false.
- The *lesson counters* (`possibleExercises` and `passedExercises`, by lesson id and language): how many exercises the lesson
  has in that language, and how many of them are passed. `setPassed()` keeps the passed counter in sync, and `registerLesson()`,
  called by the `Lesson` constructor once its exercises are loaded, recomputes both from scratch: `SessionDB` is the owner of
  these counters. They exist because `ChooseLessonDialog` needs the progress of the lessons that are not loaded, and loading a
  lesson takes seconds. Hence they survive between sessions as one `<lessonId>.summary` file per lesson in the user's
  repository, a tiny JSON object (`possibleJava`, `passedScala`... keys, null values omitted): `GitSessionKit.storeAll()` writes
  it from `lessonSummary()`, as part of `Game.saveSession()` (before each run, when switching exercise and on exit), and
  `loadAll()` reads every `*.summary` found on disk at startup -- the list of lessons is empty at that point -- into
  `lessonSummaryParse()`, which replaces the counters of that lesson (an invalid summary is ignored).

### Progress trackers

The progress tracking is driven by `Game.gitTracker`, called by `LessonRunner` once the pass/fail dialog is shown, by
`MissionEditorTabs` when the student reads a hint, and by `Game.fireCurrentExerciseChanged()`/`worldHasChanged()` when the student
switches exercise or reverts their code.

The tracker is `GitTracker`: one per running PLM instance, constructed once in `Game`'s constructor (so it is never null: tests
replace it with `Game.setGitTracker()` and a mock to disable the tracking) and registered as a `UserSwitchesListener` too. For
each PLM user, it keeps one local git repository under `SAVE_DIR/<userUUID>` (using `GitUtils`, a thin wrapper around JGit), on
a branch named `"PLM" + sha1(userUUID)`, and mirrors it to a shared server repo (`plm.git.server.url`) -- this is both the
per-student backup/sync mechanism and the anonymized activity log the PLM maintainers use to see how students actually work
through the exercises. Pushing is entirely opt-in, gated by the `plm.git.track.user` property (the student is asked once, see
`StartExecution`); everything still happens on the *local* repo either way.

Here is a list of the existing tracker events, and how `GitTracker` handle them:
- `userHasChanged()` (called once at startup and on every user switch): creates/reuses `repoDir`, sets the git remote config,
  creates the initial commit the very first time (empty, with a fixed author, date and message, so that it is the same commit on
  every machine and the sessions of a same user share their history), checks out (or creates) the user's branch, tries to `fetch`+`merge` the
  same branch from the server to resume a previous session (`GitUtils.mergeRemoteIntoLocalBranch()` resolves conflicts
  file-by-file by keeping whichever side's last commit on that path is more recent), commits a `"started"` marker, then asks for
  a push (rate-limited, see below).
- `executed(exo, outcome)`: writes/rewrites several files per exercise via `createFiles()`:
  - `<id>.<ext>.code`: student code
  - `<id>.<ext>.error`: the error of the last execution, empty if there was none. It is the compilation error if there is one (this
    includes a refusal by `verifySource()`). Otherwise, it is the execution error: either the failure of the student's code at run
    time (the error of the process, the interruption by the "Stop" button...), or, for each world that differs from the expected
    one, "The world 'name' differs" followed by the `diffTo()` between the `answerWorld` and the `currentWorld`.
  - `<id>.<ext>.correction`: the templating entity file (read again from its source)
  - `<id>.<ext>.mission`: the mission text of the exercise.
  - It then creates or deletes a `<id>.<ext>.DONE` marker file depending on pass/fail (`checkSuccess()`), then commits (JSON
    commit message, see below) and asks for a push.
- `switched()`/`reverted()`: same idea for "the student navigated away from an exercise" (re-writes its files before committing)
  and "the student clicked revert" (deletes that exercise's files instead). Their messages carry no `outcome` field (nor test
  counts or feedback): `"switched"` only tells where the student goes, and `"reverted"` that the exercise was reset.
- `exportSession()` (not a tracker event, called by the `ExportSession` action): commits the pending changes with an `"exported"`
  marker, then `SessionZip` writes the whole `repoDir`, `.git` included, in a zip file under a top-level entry named after the
  user UUID.
- `importSession()` (not a tracker event either, called by the `ImportSession` action): commits the pending changes with an
  `"imported"` marker, then merges the zip into the session, see [Moving a session between machines](#moving-a-session-between-machines) below.
- `readTip()`: same write-then-commit-then-push pattern for that UI event (see the tips in [Mission text](#mission-text)), that
  only rewrites the mission file. Its message holds the `href` of the tip, such as `#tip-2` or `#tip-python`.
- All these events end with `commitAndPush()`: it removes the deleted files from the index, adds the others, commits with the
  message of the event and asks for a push.
- `leave()` (PLM shutdown): cancels the delayed push, then does one final `addFiles()`+`commit()`+`forcefullyPushToUserBranch()` (bypassing the
  rate-limiting, since this is the last chance to sync) then disposes the JGit handle.

Commit messages are hand-built JSON blobs (`writeCommitMessage()`/`writePLMStartedOrLeavedCommitMessage()`) carrying the
exercise id, language, outcome, test counts, the initial state of the randomized worlds (in the `.map` format, by rank, for each
commit to be self-contained for the learning analytics, as `Exercise.serializeRandomizedWorlds()` provides them, also used by
the bug reports of the `FeedbackDialog`), and optional feedback -- built by string surgery (dropping the JSON library's own
leading `{`) so that a `"kind"` key always comes first and the commit list stays human-scannable from the GitHub UI. The `"plm"`
field of the `"started"` and `"leaved"` messages ends with the git commit of the PLM (`Game.getGitCommit()`, with a `-dirty`
suffix if the build had local changes, or `unknown` when not building from git), which is what it takes to replay the templating
of a past session. It is recorded in `resources/git.properties` at build time by the `git-commit-id-maven-plugin`.

Here are some the messages of a possible commit history.

- The user first starts the PLM:

    {"kind":"started","plm":"2.9.3 (20210630), commit unknown","java":"21.0.12.1 (VM: OpenJDK 64-Bit Server VM; version: 21.0.12.1+1-1-deb13u1-Debian)","os":"Linux (version: 6.10.3-amd64; arch: amd64)"}

- She then switches from the Environment exercise (that was previously passed) to the Instruction exercise:

    {"kind":"switched","switchto":"welcome.Instructions","lang":"Java","exo":"welcome.Environment"}

- The first attempt is a compile error. The faulty code is added to the commit as `welcome.Instructions.java.code` while error
  message (the possibly localized compilation error message) is saved as `welcome.Instructions.java.error`.

    {"kind":"executed","lang":"Java","exo":"welcome.Instructions","outcome":"compile"}

- The second attempt compiles but does not pass the tests. The new version of the code and the new error message (this time
  generated from `world.diffTo()`) are added to the commit.

    {"kind":"executed","passedtests":"0","totaltests":"1","lang":"Java","exo":"welcome.Instructions","outcome":"fail"}

- The third attempt passes all tests of that exercise. The file `welcome.Instructions.java.error` is removed from the disk,
  while an empty `welcome.Instructions.java.DONE` is added. The student did not rank the exercise in the interface, thus the
  "(please choose)" as a value to the exercise interest.

    {"kind":"executed","passedtests":"1","totaltests":"1","exoInterest":"(please choose)","lang":"Java","exo":"welcome.Instructions","outcome":"pass"}

- Then the student switches to another exercise, and do a failed attempt in the new one. Since this world contains a randomized
  world, the world instance is added to the commit message to make it possible to replay the student code in a future analysis.

    {"kind":"executed","exo":"sort.pancake.GatesPancake","lang":"Python","outcome":"fail","passedtests":"3","totaltests":"4","randomizedworlds":{"4":"<the .map content of the world of rank 4>"}}

- The student then asks for a hint in this exercise, reverts their code, and later leaves:

    {"kind":"switched","exo":"welcome.Instructions","lang":"Java","switchto":"sort.pancake.GatesPancake"}
    {"kind":"readTip","id":"#tip-2","exo":"sort.pancake.GatesPancake","lang":"Java"}
    {"kind":"reverted","exo":"sort.pancake.GatesPancake","lang":"Java"}
    {"kind":"leaved","plm":"2.9.3 (20210630), commit unknown","java":"21.0.12.1 (VM: OpenJDK 64-Bit Server VM; version: 21.0.12.1+1-1-deb13u1-Debian)","os":"Linux (version: 6.10.3-amd64; arch: amd64)"}

Since each commit also contains the code of the student in the files that it changes, the history of the repository tells how many
attempts were needed to pass an exercise and with which errors, how much time went by between them (the dates of the commits), which
exercises were abandoned (those attempted whose last `"executed"` event is not `"pass"`, whether or not the student switched away from them), where the hints are read, where the students revert
their code, and how they rate the exercises. The randomized worlds and the commit of the PLM itself make it possible to replay an
execution afterward.

Pushing is rate-limited (`GitUtils.maybePushToUserBranch()`, see its own comment for the incident that motivated it): at most
one delayed push is scheduled at a time (`GitUtils.pendingPush`), with a fixed delay (currently 1 minute) before it actually
pushes, run off the Swing event thread via a `SwingWorker`. The pushes themselves are serialized by `GitUtils.pushLock`, whoever
asks for them. `forcefullyPushToUserBranch()` used by `leave()` skips the delay but waits for the push already running, and
`leave()` first cancels the delayed one with `cancelPendingPush()`, so that it never runs on a disposed repository. A push
that's rejected retries once after fetching and merging the remote branch first.

### Session kits

`GitSessionKit` (`plm.core.model.session`) is the read side of the same on-disk layout `GitTracker` writes: at
startup, `loadLesson()` reads each exercise's `.code` file back into the `SessionDB` and its `.DONE` file into `studentWork`'s
pass/fail state. The code is restored with `Exercise.setEditorContent(lang, content)`, which does not load the source file, so
restoring the code does not parse the entities by itself: the bodies are named after the tab, which `newSource()` enforces. There is
no counterpart writing the code, since `GitTracker` already keeps those files current after every relevant event.
`GitSessionKit` additionally computes and reads back one `.summary` file per lesson (a `SessionDB` digest, see above; not
something `GitTracker` writes).

### Moving a session between machines

The `ExportSession` and `ImportSession` actions of the GUI move a session between machines that are never connected, without
losing the history. The zip file holds the whole local git repository of the user, `.git` included, under a top-level entry
named after her UUID (`SessionZip`). The initial commit is the same on all machines (fixed author, date and message), so that
the histories of a same user always have a common ancestor.

`GitTracker.importSession()` first saves and commits the current session. Then it fetches the user branch of the zip into
`refs/imported/` and merges it with `GitUtils.mergeIntoLocalBranch()`, that is also used for the synchronization with the
server: the conflicts are resolved file by file, keeping the side whose last commit on that file is more recent, even when
that side deleted it. Which identity survives depends on the user UUID of the zip:
- Same UUID as the current user: the zip is merged into the current session.
- Different UUID, and the current session holds no code (`isSessionEmpty()`): the user of the zip replaces the current one.
- Different UUID, and the current session holds code: the user chooses in a dialog. Keeping her identity merges the zip into
  the current session. Taking the identity of the zip moves its repository into the sessions directory as a new user, merges
  the previous session into it and removes the previous user. If any of these steps fails, the previous user becomes the
  current one again and the session of the zip is removed.

A zip that is not a session (no UUID at its top, no git repository inside) is refused before anything changes. Deletions
follow the usual three-way merge: a file deleted on one side only (a revert) stays deleted if the other side did not touch it
since their common history. If the other side modified it, the side whose last commit on that file is the most recent wins.

## How tests work

Tests live in `src/plm/test` and are compiled with the main code (see the surefire configuration in `pom.xml`). The unit tests of
a few classes sit next to them. Surefire runs only `AllTests` and `MainFrameSmokeTest`, each in its own JVM (`reuseForks=false`),
because the `Game` singleton would otherwise leak the GUI listeners of the latter into the former.

* *`AllTests`:* the suite chaining `UnitTests` and `ContentTests`.
  * *`UnitTests`:* the code of the PLM, on a minimal universe or on a few real exercises when needed.
    * *`AllSimpleExerciseTests`:* templating, compilation, execution and check on a minimal universe (`plm.test.simple`), once
      per language (`JavaSimpleExerciseTest`, `ScalaSimpleExerciseTest`, `PythonSimpleExerciseTest`, `CSimpleExerciseTest`,
      which share `SimpleExerciseTest` and `CompiledSimpleExerciseTest`). The correction compiles, runs and passes. The saved
      code can be restored into the editor without loading (so parsing) the entity, and the name of the source files must be the
      one of the tab. Wrong code, exceptions (out of bounds, null, custom) and a valid code followed by an error do not pass.
      Syntax and variable errors do not compile. The line of a stack trace frame is the editor's one. Every language also checks
      the line of a compilation error, and Python and C check that the `IMPORT` section is honored.
    * *`EntityTemplateParserTest`:* parsing of the `BEGIN/END` markers (`TEMPLATE`, `SOLUTION`, `IMPORT`, `REMOTE`) and the errors
      raised on invalid markup.
    * *`IndentationTest`:* the tab expansion and reindentation helpers used by the Python templating.
    * *`GitTrackerTest`:* the files written and deleted by `GitTracker`, the `.DONE` marker, the PLM commit in the messages, and the outcome that
      it reports for the events that are not executions (the one of the last execution in the current language, or an empty one).
    * *`GitUtilsTest`:* branches, fetch, merge conflicts and push on local repositories.
    * *`GitTrackerImportTest`:* with two trackers in temporary directories that stand for two disconnected machines, the initial
      commit is the same on both, `importSession()` merges a zip into the local session, resolves a conflict in favor of the most
      recent file, keeps the local identity or adopts the one of the zip (keeping the local work), and refuses to replace an existing user.
      A corrupt zip, a zip without git repository, or a failure after adopting the identity of the zip leave the local session
      and user intact, without temporary directory nor session of the zip. A deletion on one side only survives the merge, and
      a modify/delete conflict keeps the most recent side.
    * *`SessionZipTest`:* a session directory survives the trip through a zip file, a zip that is not a session is refused, and so
      is an entry that would leave the target directory.
    * *`PrimitiveRegistrationTest`:* the primitives are indexed by name and sorted, inherited ones included, and cached. The same
      declaration in two interfaces is one primitive, while the same name with another signature is rejected. The parameter
      names are the declared ones (`forward(steps)`), which fails if `-parameters` is lost.
    * *`PrimitiveAliasesTest`:* the primitive names of a catalog are read (fuzzy entries ignored) and added to a glue. An alias
      calls its canonical primitive and appears once even if several locales share it, while a name that is not an identifier
      (decomposed accents included), a keyword, or a name designating two primitives is rejected.
    * *`GlueGenerationTest`:* generating the glue of every universe in every language gives the files that the build packed.
    * *`CommandExecutorTest`:* a command calls the primitive and writes its result back (nothing for a void primitive). Spaces in
      the arguments are kept, enums travel as ordinals, and atomic values are converted where a string is expected. An unknown
      primitive or arguments of the wrong type fail the run, a forbidden primitive is refused before being called, a
      `PrimitiveRefusedException` or another `ExplainedException` is reported as is, and any other exception is reported with
      the call that raised it.
    * *`ApiGatingTest`:* on test buggles, the primitives forbidden by `forbidTeleportation()` and `forbidMultiStep()` are refused
      by `CommandExecutor` with an explanatory `PrimitiveRefusedException`. `forbid()` rejects an unknown primitive, the forbidden
      primitives are read-only and forbidden again by every new instance, and the likely mistakes (`Left()`, `penDown()`...) are
      explained. The documentation of the world hides the forbidden and undocumented primitives, and orders the groups as declared.
    * *`PosixWorldTest`:* the kernel of the POSIX universe (files, TCP and UDP sockets, deadlocks, binary data), its scripted and
      program peers (IRC server included), and the comparison of its worlds, by calling the primitives of the student's process.
    * *`LangCMessagesTest`:* the compiler messages show the real names of the functions that a C glue renames with macros.
    * *`LessonRunnerTest`:* `LessonRunner.runExercise()` returns the outcome of the execution, a compilation error included, and a
      failure with a "Not run" message if the execution was interrupted, going through the expected states of the game. The dialogs
      and the tracker are not tested, as they need a display.
    * *`PancakeRandomizedTest`:* a randomized pancake world is reported as such by `isRandomized()`, also after its copy.
    * *`LightBotProgramTest`:* the text of a LightBot program is parsed and written back, whatever its length.
    * *`GitSessionKitTest`:* with a repository of a user in a temporary directory, `loadLesson()` restores the saved code and the
      successes into the `SessionDB` without loading the entities (and without `loadAll()` having run), and `loadAll()` reads the lesson summaries.
      It first waits for the answer computation, which loads the entity in one language in the background.
    * *`SessionDBTest`:* the editor contents stored by exercise and language do not interfere, a body is stored as is,
      reverting an exercise forgets its contents only, the editors are told of the changes, the passed exercises are counted per
      lesson and language (`registerLesson()` included), and the lesson summaries are written and parsed back (an invalid one is ignored).
    * *`ValueFormatterTest`:* the value comparison and formatting of the bat universe.
    * *`ColorMapperTest`:* the colors read by name or by components, numbered for the protocol, and named in the messages.
    * *`PoFileTest`:* `PoFile` reads the entries as gettext writes them (strings over several lines, contexts, fuzzy flags),
      without the obsolete entries and the plural forms.
    * *`ValueSerializerTest`:* the Java side of the serialization of values exchanged with the remote entity.
    * *`ValueSerializerInteropTest`:* the Python and C sides read what Java serializes, and write back texts that Java reads as the
      same values (doubles may be written differently). It also compiles and runs `value_serializer_test.c`, the unit tests of the
      C side. It needs `python3` and `gcc`.
    * *`MethodsDogHouseSourceCheckTest`:* `verifySource()` refuses the code unless it calls `left()` exactly once, ignoring
      comments and strings, in the four languages. Its alias in the current human language counts as well (`gauche()` in French).
      The check is called directly, and only one refusal goes through `compileRunCheck()`, as compiling every case is slow.
  * *`ContentTests`:* the pedagogical material itself (lessons, exercises, mission texts and their translations) rather than
    the code, with the test methods running in parallel. They catch broken content, such as a correction that no longer matches
    its `-answerN.map` or a translation that breaks the markup.
    * *`ExoTestJavaLang`, `ExoTestScalaLang`, `ExoTestPythonLang`, `ExoTestCLang`:* for every exercise, `compileRunCheck()` of the
      correction entity must pass in that language. They share `ExoTest`, which lists the exercises of the lessons offered to the
      students (`Lesson.OFFERED`, also shown by the lesson chooser), but LightBot (see below). The Python and C ones also fail when
      the exercise has no entity file in their language, and the Turmites get a longer timeout.
    * *`MissionMarkupTest`:* in every mission file, translations included, the `[!langs]...[/!]` blocks are balanced and only name
      known languages, and no tag is malformed (such as `[/!` without its closing bracket, or `[java]` without its `!`).
    * *`TranslationsTest`:* the work of the translators, who are not all programmers, does not break the PLM. The primitive names
      of every `l10n/engine/*.po` can be added to the glue of every universe, and their messages remain valid `MessageFormat`
      patterns using the same arguments as the English text. In every `l10n/missions/*.po`, even for the languages
      that po4a does not generate, the translations keep the well-formed `[!langs]...[/!]` blocks of the English text and call
      each of its primitives under its English name or its alias in that language. The translations of the engine keep the texts
      that their comments for the translators ask to keep unchanged (such as the URLs that Bob gives in `TcpFramingIrc`), which
      must be in their English message, and the English messages taking arguments double their apostrophes, as `MessageFormat`
      requires.
    * *`GatedExercisesTest`:* the exercises that gate their API (`Array1`, `LoopFor`, `TraversalByColumn`, `MethodsDogHouse`,
      `LinearHanoi`) refuse a call that would defeat their goal.
    * *`LightBotLessonTest`:* the LightBot boards are puzzles without correction: each one loads, and has lights that the
      empty program of a new student leaves off.
    * *`WorldDiffTest`:* for every exercise, the initial worlds equal their copy, and `diffTo()` explains how they differ from the
      answer worlds, as it does for a failing student. The lander is skipped: its worlds are judged by `winning()`, not by
      equality.
* *`gui.MainFrameSmokeTest`:* the main window comes up. It needs a display (`xvfb` in CI).

Only the *correction* entity is compiled by the `ExoTest*Lang` tests. The student path (editor content injected into the
template) is exercised by the `SimpleExercise` tests and by `MethodsDogHouseSourceCheckTest`.

A stale `-answerN.map` is reported as a broken test, not fixed automatically: decide whether the entity or the cache is wrong. In
the latter case, delete the `.map` file and run the tests twice: the first run regenerates it (and passes trivially), the second
one checks the correction entities against it.

## Languages & runtime versions

- **Build/host**: Java 17 (`maven.compiler.release=17`), built with Maven (`pom.xml`).
- **Student languages**: each is a `ProgrammingLanguage` subclass in `plm.core.lang` (`LangJava`, `LangScala`, `LangPython`,
  `LangC`). Whatever the language, the student's code runs in its own process and calls the primitives over a socket (see
  "How an exercise executes" and "Remoting" above). What differs is how the code gets compiled:
  - **Java**: compiled in-process with the JDK compiler (`javax.tools`), then run with `java -cp`.
  - **Scala**: `scala3-library_3`/`scala3-compiler_3` 3.9.0 (LTS), compiled in-process by driving `dotty.tools.dotc.Driver`
    with `-no-indent` (braces only, since many entities mix tabs and spaces), then run with `java -cp` like Java.
  - **Python**: checked with `python3 -m py_compile`, so that syntax errors are reported as compilation errors before the
    run, then run by `python3` (Python 3 must be on the PATH).
  - **C**: compiled and linked by an external compiler (with AddressSanitizer if it supports it), then the executable is run.
    The compiler is given by the `c.compiler` property (`gcc` by default). Its warnings are displayed on the console, unless the
    picky mode (`compiler.picky` property, checkbox of the Exercise menu, always on in the tests) turns them into compilation
    errors.
- **Line endings**: the outputs of the student are compared with the ones of the correction, so every language writes `\n` at
  the end of the lines, even on Windows: the JVMs run with `-Dline.separator=\n` (`JvmTemplatedLang.UNIX_LINES`, read by
  `println()`, `%n` and `BufferedWriter.newLine()`), the Python glue of the POSIX universe opens its text streams with
  `newline="\n"` when they write, and the C glue writes its bytes as they are.
- Adding a new language: see `https://github.com/oster/PLM/wiki/Adding-a-new-programming-language` and extend
  `plm.core.lang.ProgrammingLanguage`. Be warned that you will have to adapt the mission text of every exercise, as they contain
  language-specific chunks.

# Translating the PLM

The translated mission files (`*.fr.html` etc.) are generated by po4a: never edit them. The easiest is to use
[weblate](https://hosted.weblate.org/projects/programmers-learning-machine/) for that. You have two translation components: The
'PLM engine' contains all texts that is displayed in the interface while the 'missions and exercises' contains the text of all
exercises implemented in this environment.  Even if all lessons are grouped together, you probably want to translate the
"welcome" lesson first.

The engine component also holds the names of the primitives (context `primitive`), which students can then call in your
language. Each name must be a valid identifier and must not be the name of another primitive of the same world: the tests
(`TranslationsTest`) catch the mistakes. A name has a single translation, shared by all worlds (`isSorted` is translated
once for pancakes and flags). Use the same names in the mission texts.

Every change to the engine will automatically be included in the [versions built on
appveyor](https://ci.appveyor.com/project/mquinson/plm) (once weblate commits your work, which may take one or two day unless
someone asks the robots to do so earlier). The translations of the mission texts is not integrated automatically, and someone
should run po4a locally and commit the modified files. po4a cannot be run automatically on appveyor because of portability
issues.

Every time that you think you reached a milestone in your translation (e.g., completion of the engine or of any given lesson),
you should drop an email to Martin Quinson so that he publishes your work in a new release of the PLM.

To change the English text without losing the translations, apply the same change to the `msgid` of the matching entries in
`l10n/missions/plm.pot` and in every `l10n/missions/*.po`, and adapt each `msgstr` accordingly. po4a then finds every `msgid`
unchanged, and generates the translated files with your change. Some pitfalls:
- The `msgid` must be exactly what po4a extracts from the html: the lines of a paragraph are joined with single spaces, while the
  content of `<pre>` is kept verbatim (these entries are flagged `no-wrap`, and their newlines are written `\n`).
- An entry gathers all the files that contain the same text (several `#:` references). If your change makes two `msgid` identical,
  merge their entries: duplicate `msgid` are an error.
- Some translations translate the primitive names too (e.g. `pas()` in French). Use the names given in the `primitive` context of
  `l10n/engine/<lang>.po`, since they are the ones that the students can call.
- The `[!<langs>]...[/!]` markup appears verbatim in both `msgid` and `msgstr`, and must be changed in both.
- `msgfmt -c --statistics -o /dev/null l10n/missions/fr.po` checks a catalog. Compare its counts before and after running po4a: a
  new fuzzy or untranslated entry means that a `msgid` does not match the html anymore.

# Extending the PLM

The pedagogical guidelines for the design of lessons and exercises are given in the [pedagogical
documentation](PEDAGOGY.md#designing-exercises).

## Adding a new lesson

A lesson is a package under `src/lessons/` (e.g. `lessons.turmites`) containing:

- `Main.java`: a subclass of `Lesson` whose `loadExercises()` lists the exercises with `addExercise(exo)`, in the order of the
  lesson. `addExercise(exo, previous)` makes an exercise depend on a previous one in the lesson graph instead.
- `Main.html`: the presentation of the lesson (*Help/About this lesson*). Its first `<h1>` gives the name of the lesson.
- `short_desc.html`: the short description shown by the lesson chooser.
- `icon.png`: the icon of the lesson in the lesson chooser.

Then:

- Add the lesson to `Lesson.OFFERED`, which defines the rows of the lesson chooser. The `ExoTest*Lang` tests then check all its
  exercises.
- Add `Main.html` and `short_desc.html` to `po4a.conf`, along with the mission texts of the exercises, so that they get
  translated.
- Each exercise lives in a sub-package, see below.

## Adding a new exercise

### Defining an exercise

The Moria exercise is representative of what you want to do
https://github.com/BuggleInc/PLM/tree/javaUI/src/lessons/welcome/summative

**Everything works because the files have the right name.**

- Moria.html: mission text in English, created either manually or with the editor (see below).

### API gating: restricting or adapting the primitives

Some exercises hide or alter a usual primitive for pedagogical reasons, which we call *API gating*. See the [pedagogical
documentation](PEDAGOGY.md#designing-exercises) for its motivation and some examples.

**How to do it.** Everything goes in the exercise's Java entity (but for case 5, which goes in the exercise class), whatever the
languages the exercise offers. Do not put checks in the Python, Scala or C entities: they would run in the student's process,
where the translations are not available (and the entities of the non-Java languages ignore everything that precedes `BEGIN
REMOTE`). Messages go through `Game.i18n.tr()` with a literal string, so that they get extracted for translation. There are five
cases:

1. *Forbidding a primitive altogether*: call `forbid(primitiveName, reason)` from the constructor of the entity. The student gets
   "Sorry Dave, I cannot let you use <primitiveName> in this exercise. <reason>". Buggle entities can call
   `forbidTeleportation()` to forbid `setX()`, `setY()` and `setPos()` at once, and `forbidMultiStep()` to forbid `forward(n)` and
   `backward(n)` while keeping `step()` and `stepBack()`. Turmites forbid every buggle primitive they don't need
   (`TurmiteEntity.forbidBuggleExtras()`), which also cleans their documentation.
   ```java
   public WallFollowerMazeEntity() { forbidTeleportation(); }
   public MyEntity()               { forbid("brushDown", Game.i18n.tr("Your buggle must not draw in this exercise.")); }
   ```
   An unknown primitive name makes the construction of the entity fail, so typos get caught by the exercise tests.
2. *Refusing some calls of a primitive*: override the Java method that the primitive ends up calling, and throw an
   `PrimitiveRefusedException`. For example, `LinearHanoiEntity` refuses the direct moves between the first and the last slot:
   ```java
   public void move(int from, int to)
   {
     if ((from == 0 && to == 2) || (from == 2 && to == 0))
       throw new PrimitiveRefusedException(Game.i18n.tr("
            Sorry Dave, I cannot let you move disks between slots 0 and 2 directly. Use the intermediate slot in all moves."));
     super.move(from, to);
   }
   ```
3. *Replacing or extending a primitive*: override it and do what you want, as in `CyclicHanoiEntity`, whose `move()` calls
   `cyclicMove()`, which performs the additional verifications:
   ```java
   public void move(int src, int dst) { cyclicMove(src, dst); }
   ```

4. *Explaining a likely mistake*: declare a primitive that only refuses the call. `Left()` and `Right()` (wrong case), as well as
   `penDown()` for the buggles and `brushDown()` for the turtles, are primitives whose default method throws an
   `PrimitiveRefusedException` with the explanation. Being primitives, they exist in the glue of every language, so students get
   the translated message instead of a compilation error.

5. *Verifying the source code*: override `Exercise.verifySource(String code)` in the exercise class (not in the entity) and throw a
   `PLMCompilerException` to refuse the code of the editor. It is called once the student's code compiled and before it executes,
   so it applies to every language, and the message is shown as a compilation error. `MethodsDogHouse` thus requires exactly one
   call to `left()`, ignoring comments and strings. Since students may call the primitives under their translated name, such a
   check must also look for the alias of the current human language (`Game.i18n.trc("primitive", "left")`):
   ```java
   @Override public void verifySource(String code) throws PLMCompilerException
   {
     if (!isValid(code)) // a regex search on the code, once comments and strings are blanked out
       throw new PLMCompilerException(Game.i18n.tr("Your code must call left() exactly once."));
   }
   ```

**How it works.** The student's code only sends the name of the primitive and its arguments (see
[Remoting](#remoting-how-the-students-entity-talks-to-the-plm) above). `CommandExecutor`, which acts as the gate, calls the Java
method of the real entity by reflection, so an override applies to every language without any glue. `forbid()` stores the name
and the reason in the entity, after checking that the entity has a primitive of that name
(`PrimitiveRegistration.getMinimalPrimitiveForEntity()`, which is cached). Since the worlds are copied by instantiating the
entities again, the constructor runs for every copy. `CommandExecutor.command()` looks up the forbidden primitives right after
parsing the name, and fails the run with the translated message. `Entity.getForbiddenPrimitives()` gives them to other parts of
the PLM, such as the documentation of the world (Ctrl-H), which hides them.

### Mission text

You can either write the text manually in html, or use the PLM mission editor, that make it easier to write mission texts that
work for more than one programming language. You can start it with:
  java -cp /usr/share/java/plm-*.jar plm.core.ui.editor.MissionEditorApp

**Language-specific markup.** A single mission file serves every programming language. `MissionMarkup.filter()` keeps the
content of a `[!<langs>]...[/!]` block when the current language is among `<langs>`, and removes the whole block otherwise.
`<langs>` lists some of `java`, `python`, `scala` and `c` (lowercase), separated by `|` in any order; text meant for all four
languages simply goes out of any block. `[!thelang]` is replaced by the name of the current language. For example:

    [!java|c]void [/!]step() or [!java|c]void [/!]forward([!java|c]int [/!]steps[!scala]:Int[/!])

reads `void step() or void forward(int steps)` in Java and C, `step() or forward(steps:Int)` in Scala and `step() or
forward(steps)` in Python.

Blocks can be nested, as they are resolved from the innermost: `[!java|scala|python]forward()[!java];[/!][/!]` gives `forward();`
in Java, `forward()` in Scala and Python, and nothing in C. The debug mode of the PLM and the mission editor display all the
blocks, with a color per set of languages. `MissionMarkup` also lists the mistakes in the markup of a text, for the tests of the
mission texts and of their translations.

**Tips.** A mission can hide some help behind a link, that the student opens on demand (see the [pedagogical
considerations](PEDAGOGY.md#scafolding-tools)):

    <div class="tip" id="tip-python" alt="Give me the complete code of that generator">
    <pre>def lines(sock): ...</pre>
    </div>

When loading the mission, `Lecture` extracts each such `div` into a map indexed by `#` and its id, and replaces it with a link
`<a href="#tip-python">` whose text is the `alt` attribute (or "Show Tip" without it). A click on a link starting with `#tip-`
(`MissionEditorTabs`) shows the tip in a `TipsDialog`, after resolving its `[!lang]` blocks, and records the event in the
student's history (`GitTracker.readTip()`, see [Progress trackers](#progress-trackers)). The rules follow from this mechanism:
- The id starts with `tip-`, followed by letters, digits, `_` or `-` (such as `tip-1` or `tip-python`). It must be unique in the
  mission, as two tips with the same id overwrite each other, and it must stay the same in the translations. The student never
  sees it, but it ends up in the tracking data: a meaningful name tells which tip was read without opening the mission.
- The `div` must hold no other `div`, since the tip ends at the first `</div>`, and its attributes must be written exactly in
  this order, with double quotes, or the `div` stays in the text as is.
- A tip placed in a `[!lang]` block only appears in these languages, with its link. Its content may also hold `[!lang]` blocks.
- The `alt` text is translated with the rest of the mission, while "Show Tip" is not: always give an `alt`.

## Designing a new universe

Extend at minimum: `World` (state/data), an `Entity` subclass (ancestor of correction entities, exposes primitives), a
`WorldView` (graphical rendering), and usually a `WorldPanel`/`EntityControlPanel` for interactive controls. Annotate the root
entity class with `@Glue("RemoteXxx")`: `CodeCreation` then generates that glue in every language. Document the universe with an
HTML file following the same convention as mission texts, where `[!primitives/]` stands for the table of the primitives,
generated from their `@Primitive` annotations (see [Primitives](#remoting-how-the-students-entity-talks-to-the-plm) above), and
`[!colors/]` for the table of the colors. A universe can offer its own placeholders by overriding `World.expandPlaceholders()`,
which runs before the `[!langs]` blocks are resolved (so that the generated content may hold some), and load the html file next
to any class with `World.documentation()`, translated as the one of the world. The placeholders must also be listed in
`MissionMarkup`, which otherwise takes them for blocks. `PosixWorld` uses it for the `[!protocols/]` documentation.

Existing universes remain small (a few hundred to ~1500 lines including the buggle map editor) because all non-functional
plumbing (compilation, templating, session handling) is factored into `plm.core`.

### World I/O and the answer cache

Loading a lesson would be slow if every exercise had to compile and run its correction entity to get its `answerWorld`.
Universes implement world I/O to avoid this: `ExerciseTemplated.doComputeAnswer()` first loads the worlds that it can from
`src/<worldFileName>-answerN.map` (`loadCachedAnswers()`, N being the rank of the world in the exercise), and only the missing
or broken ones are computed by the correction entity (`computeAnswers()`, that compiles it with `compileCorrection()`, as
`runDemo()` does), then written back for next time (`writeAnswerFile()`). Each world is handled on its own: one missing file
 does not force recomputing the others. Nothing invalidates these files: it is up to the tests (see above) and to the
maintainers.

To support it, a universe overrides `haveIO()` (returning true), `parse(reader, path)` and `writeToFile(writer)` of `World`.
Universes that do not override `haveIO()` get their answers computed at each load. You should implement IO in your universe
before shipping it in the PLM.

* The format is textual and specific to the universe, for the files to stay readable, diffable, and independent of the Java
  class layout (Java serialization would break at the first refactoring).`World` provides `readField()` and `readInts()` to
  parse the `Key: value` lines, and `writeField()` to write them. The textual form of a value that is not a plain field belongs to
  the class of that value, e.g. `Operation.parse()` with the `toString()` of the sorting operations, or `BatTest.toMapLine()` and
  `BatTest.fromMapLine()`.
* A universe that reads files should have a private constructor taking the final state of a world, so that `parse()` does not need
  to build a world only to overwrite it. The public constructors of the exercises can delegate to it.
* `World.writeToFile(File)` writes a temporary `<name>.tmp` file and then moves it over the target, so that a failure never leaves
  a partial map behind.
* `World.readFromFile()` opens the file and calls `parse()`. A `NumberFormatException`, `ArrayIndexOutOfBoundsException` or
  `IllegalArgumentException` raised while parsing becomes a `BrokenWorldFileException`, so `parse()` only needs to throw it for
  the problems that it detects itself. A universe that needs another way of reading may override `readFromFile()` instead.
* The file must hold what is needed to compare with `equals()`/`diffTo()` and to display the world, including its history if the
  views show it (e.g. the operations of the sorting worlds). It does not need to hold what only matters when an entity runs
  (e.g. the starting position of the turtles).
* A malformed or missing file is reported on stderr and the world is recomputed.
* A universe may store less than the state if the rest can be replayed: the baseball worlds store their initial field and their
  moves, and rebuild the field by playing them. The bat worlds cannot store a string value containing a tab or a line break:
  `writeToFile()` then fails without writing anything, and the exercise is simply not cached.
* The initial worlds must be reproducible, because a cached answer is only valid for the initial world it was computed from. Do
  not use an unseeded random generator in `setup()`: seed it with something stable, such as the name of the world.
* A world that must stay random calls `setRandomized()`, which `isRandomized()` reports. Such a world is never read from nor
  written to disk: its answer is computed at each load, at the cost of compiling the correction entity. The sorting universes
  provide `randomize()` for that, returning the world to be usable in the exercise's list of worlds. By convention, each of their
  exercises randomizes its last world (or the one named "random 15 pancakes" in the pancake exercises with fixed hard cases), so
  that the entities are also tested on unforeseen inputs.
* `worldFileName` defaults to the name of the exercise class, and `answerFile(rank)` builds the name of the cache files from it.
  Exercises sharing one class (e.g. `TurtleGraphicalExercise`) must set it to a distinct value, or they would overwrite each
  other's files: `doComputeAnswer()` throws an `IllegalStateException` when two exercises use the same one.
* `Exercise.serializeRandomizedWorlds()` gives the initial state of the randomized worlds in the `.map` format. It is added to the
  commit messages of the learning analytics and to the technical information of the bug reports, as the maintainers could not
  rebuild these worlds otherwise.

### Comparing turtle worlds

`TurtleWorld.diffTo()` compares the shapes on normalized copies of the lists, leaving the worlds untouched: they are sorted, the
duplicates are removed, and the lines that lengthen each other or that cover each other are merged into one by `mergeLines()`,
until the amount of shapes is stable. This way, drawing a line in one or several segments gives the same result. The colors are
not compared during the merge.

### The POSIX universe

The `plm.universe.posix` universe, used by the networking lesson (`lessons.network`), teaches the system calls on files and
TCP sockets, without intercepting a real system: the student's process acts on a simulated kernel (`PosixWorld`), and the other
programs are peers (`Peer`), following a script or written in Java. Its pedagogical choices are described in the [pedagogical
documentation](PEDAGOGY.md#system-programming).

* **The kernel**: `PosixWorld` holds the regular files and the processes: the student's one and the ones of the peers. Each
  `PosixProcess` has its machine address, its descriptor table and its last error. The descriptors point to open file
  descriptions (`FileDescription`): `StandardStream` (0, 1 and 2 at first), `RegularFile`, and the sockets (`InetSocket`) of
  TCP (`Socket`) and UDP (`DatagramSocket`, whose datagrams arrive whole and are lost when no socket waits for them, or truncated
  when the buffer of `recvfrom()` is too small; one used before `bind()` gets an ephemeral port, from a start that depends on
  the machine's address, so that it differs between the machines). The kernel executes the
  system calls of all the processes with the same code, following the Linux semantics and constants, and returns -1 with an
  error name (e.g. `ECONNREFUSED`) on failure. The data is kept as bytes, one `char` per byte (ISO-8859-1): the trace shows it
  as strace does (unprintable bytes in octal), and the view decodes the files and the outputs from UTF-8.
* **Time**: the world has a clock. The student's system calls take no time, but `sleep()` and the blocking calls do: when nothing
  can progress, the clock jumps to the next wake up of a peer. Each scenario thus has a single causal history. A call that would
  block forever raises a deadlock (listing the state of the peers), and 1000 refused `connect()` in a row without the clock moving
  raise a busy loop error. Both are `ExplainedException`, shown to the student without the call that raised them.
* **The scripts**: each peer has a script written in a text block, with the syntax of the trace (one call per line, `//`
  comments, strings with the escapes `\n`, `\r`, `\t`, `\"` and `\\`), whose steps are executed through the system calls of the
  peer's process. A server peer has its listening socket on descriptor 3, which only listens once the script reaches its first
  `accept()` (the connections are refused before), and accepts its connections on the lowest free descriptors (4, then 5...); a
  client has an unconnected socket on 3, can create more with `socket()`, and connects them to the student's machine
  (`PosixWorld.STUDENT_IP`). The parsing follows the descriptors as the kernel allocates them, so the errors (such as sending on
  a descriptor that is not a connection) are reported with their line when the exercise is loaded:
  ```java
  Peer.server("10.0.0.1", 80, """
      accept(3)
      sleep(1)
      sendInPackets(4, "Hello, world!", 7, 1) // send(), then transmit() 7 bytes after each pause of 1s
      close(4)
      """)
  ```
  `Peer.udpServer()` and `Peer.udpClient()` give the same over UDP: their datagram socket is on 3 (bound to its port for a
  server), `recvfrom(3)` waits for a datagram and receives it whole, and `sendto(3, "...")` sends one at once, to the student's
  port for a client, or to the sender of the last datagram received for a server.
  The peers act as far as they can before and after each system call of the student (`PosixEntity`), and each of their steps
  is animated on its own (`PosixWorld.advancePeers()`). The student writes a function whose parameters (such as the address
  and the port of the server) are given by each world with `PosixWorld.setParameters()`, along with its peers, so that
  hard-coded values fail.
* **The programmed peers**: the servers of real protocols (answering each request as it deserves) are Java programs extending
  `ProgramPeer`, written as event loops: `start()` typically listens on their ports, and each call to `act()` does at most one
  action and tells whether it did one. Their helpers (`listen()`, `accept()`, `peek()`, `receive(fd, length)`, `receive(fd, delimiter)`,
  `ended()`, `send()`, `sendInPackets()`, `close()`, `ascii()`, `note()`) call the kernel and trace these calls as the student's ones,
  without blocking: `accept()` returns -1 when no connection waits, `peek()` shows what arrived without receiving it, and
  `receive(fd, delimiter)` returns null until the delimiter arrived. The data of `send()` reaches the
  student at once, while `sendInPackets()` lets the network carry it in packets after pauses, to make the framing matter. Over
  UDP, `bindDatagrams()` binds a datagram socket, `receiveDatagram()` returns the next datagram with its sender (or null), and
  `sendDatagram()` sends one, which arrives at once. `note()` adds a line of the program to the trace, such as what it understood
  of a binary request. Their
  state is in the fields of their class, which their copy constructor copies (after the one of `ProgramPeer`), and `waiting()`
  tells the trace what they wait for. `PosixWorldTest.ShoutServer` is a small example.
* **The documentation of the protocols**: `[!protocols/]` in `PosixWorld.html` stands for a section "The servers of this world"
  holding, once per class of `ProgramPeer` among the peers of the world (in their order), the html file next to that class
  (`IrcServer.html`, `HttpServer.html`, `FtpServer.html`, `DnsServer.html`): its heading (such as "The IRC protocol"), the framing, the commands,
  the replies and the errors, and an example session to the byte. The section is absent from the worlds without such peers. A
  new server should come with its reference, listed in `po4a.conf`, which describes the protocol without revealing the scenario
  of an exercise (such as the words that a member of an IRC channel expects).
* **The IRC server** (`IrcServer`, named `irc.buggleinc.com`) is exact to the byte as the usual servers (RFC 2812): a translated
  `NOTICE` greeting each new client (so that a client receiving before sending gets a hint instead of a deadlock), registration
  with `NICK` and `USER` and its welcome burst, `JOIN`, `PART`, `PRIVMSG`, `NAMES`, `PING` and `QUIT`, and the usual numeric
  errors. It splits the lines on `\n`, ignoring a `\r` before it. The exercise gives its channels with their topic and their
  simulated members (`channel()`), the lines these members say some seconds after a client joined the channel (`say()`, so that
  each client receives the whole chat), the answer of a member to the messages containing some words (each in one of its forms,
  such as its translation and the English word, whatever their case and accents) and to the other ones (`answer()`), a line
  addressed to the client who did not write to that member yet (`address()`), the hints of a member to the client who wrote to
  another one without getting its answer, one more after each failure (`hints()`), and possibly the size of the packets cutting
  the lines of the members, one per second (`packets()`). The addressed lines and the hints are `MessageFormat` patterns, whose
  `{0}` is the nickname of the client, and whose `{1}`, `{2}`... are the words expected by the other member (for the hints), so
  that a hint can give an exact sentence that stays consistent with the translated words. The texts, which may be translated,
  lose their accents since the servers send them in ASCII (`ProgramPeer.ascii()`). A `PRIVMSG` whose text holds spaces without
  its `:` is refused with a notice telling how to write it, where a real server would only send its first word.
* **The HTTP server** (`HttpServer`, software `plm-httpd/1.0`) serves static files (`file()`) with `GET` and `HEAD`, exact to the
  byte as the usual servers: its responses give `Content-Length`, the connections persist in HTTP/1.1 (unless `Connection:
  close`) and close after the response in HTTP/1.0 (unless `Connection: keep-alive`), and the errors are 400 (also for an
  HTTP/1.1 request without `Host`), 404, 405 and 505, with a small HTML page. It accepts the lines ended by `\n` alone. Its
  `Date` starts on 2024-01-01 and follows the clock of the world. The idle connections stay open unless `keepAlive()` gives a
  timeout, so that a client waiting for the end of the stream instead of reading `Content-Length` ends in a deadlock, which
  tells it. `packets()` cuts the responses as the one of the IRC server.
* **The FTP server** (`FtpServer`, software `plm-ftpd 1.0`) serves files (`file()`, whose directories exist then) in passive
  mode, exact to the byte as vsftpd: anonymous login (`USER anonymous`, then `PASS` with anything), `PASV` (227, the port being
  p1*256+p2) or `EPSV` (229) opening a listening socket on a new port (40000, then 40001...) for each transfer, `RETR` and `LIST`
  sending the data on the data connection and closing it before confirming with 226, `SYST`, `TYPE`, `PWD`, `CWD`, `QUIT`, and
  the usual errors (500, 530, 550, 425...). A transfer asked before the client connected the data connection waits for it. Its
  welcome spans several lines (`220-` then `220 `), which `welcome()` can change. `packets()` cuts everything it sends, the
  replies and the data.
* **The DNS server** (`DnsServer`) is authoritative for one zone over UDP (RFC 1035), without recursion. The exercise gives its
  records (`a()`, `txt()`, `srv()`); it answers the asked type (or all the records for ANY), NOERROR without answer for an
  existing name without such records (including the names that only have descendants), NXDOMAIN for a missing name, and REFUSED
  outside its zone. The TXT records of the asked name come in the additional section of the other answers about it, so that the
  hints of a scenario are found without guessing their type. It never compresses the names. It notes each query and answer
  decoded in the trace (`note()`), and explains the malformed queries, answered FORMERR (numbers in the wrong byte order, a name
  written as text or without its final zero byte, bytes after the question...). A datagram that is not a query is ignored, with a
  note, as real servers do.
* **The network**: a connection is a pair of sockets pointing to each other, each with its send and receive queues, created by
  `connect()` in the backlog of the listening socket until `accept()` takes it. A peer's `send()` only fills the send queue of
  its socket, and `transmit(fd, n)` carries at most `n` bytes to the receive queue of the other end, in one packet. The end of
  the stream follows the data sent before the `close()`. This way, a short read is always caused by data still on its way,
  visible in the world view. What the student sends reaches the peer at once (`PosixProcess.scriptedNetwork`).
  `PosixWorld.addPeer()` warns when a script leaves some sent data untransmitted.
* **Comparing the worlds** is semantic: the standard output and error, the files, the state of the peers (their position in the
  script, and everything that arrived on their connections, received or not) and the open descriptors are compared, but not the
  numbers of the descriptors, so a program opening its descriptors in another order still wins. An exercise can restrict the
  comparison to some aspects with `PosixWorld.comparing()`, for example to the output and the descriptors when the student may
  talk with a server in several ways: `winning()` and `diffTo()` then ignore the rest, while `equals()` still compares
  everything.
* **The C glue** is hand-written (`RemotePosixGlue.h` and `RemotePosixGlue.c`, with `@Glue(wrapped = true)`): it offers the real
  POSIX signatures, renames the student's calls with macros (`#define recv plm_recv`, which `LangC.withRealNames()` hides from
  the compiler messages, along with `-ftrack-macro-expansion=0` if the compiler accepts it, so that the errors are located where
  the student called the function), converts `struct sockaddr_in` and the local constants to the protocol ones, copies the
  received bytes in the caller's buffer, and sets the real `errno` from the undocumented `lastError()` primitive. It exposes
  `getParamString()` and `getParamInt()` to the code of the entity that calls the student's function (the generated functions of
  a wrapped glue are private). It also intercepts the output functions of `stdio.h` on the standard streams (`printf()`,
  `fprintf()`, `puts()`, `fputs()`, `putchar()` and `perror()`), unbuffered, as the libc would otherwise write behind its back.
  Its `fopen()` and `fdopen()` give real streams of the libc, buffered as usual, whose reads and writes call the system calls of
  the world (`fopencookie()` of the glibc, which `LangC` enables with `-D_GNU_SOURCE`, or `funopen()` on macOS): the student can
  use `fgets()` or `fscanf()` on a file or a socket. The C library of Windows has no such custom streams: the glue gives its own
  streams there (`PLM_OWN_STREAMS`), whose address is passed as a `FILE*`, and renames the functions of `stdio.h` working on
  streams (`fgets()`, `fread()`, `fwrite()`, `fflush()`, `fclose()`, `setvbuf()`...) to handle them, passing the other streams to
  the C library. `fscanf()` is not available on these streams, which it explains once on the PLM console (the real standard
  error, through `explain()`). `vfprintf()` is intercepted everywhere, as `fprintf()`. `explain()` also tells the usual mistakes
  in filling a `struct sockaddr_in` (`sin_family` forgotten or converted with `htons()`, size of a pointer, address 0.0.0.0 or
  port 0), which the `errno` alone hardly tells.
  TODO: fseek(), ftell() and rewind() are not renamed, so the unintercepted version may crash when used on our own FILE*.
* **The Python glue** (`RemotePosixGlue.py`, appended to the generated functions renamed `_plm_remote_xxx`) substitutes the
  system modules at import, so that the student's code uses them as usual: `sys.modules["socket"]` becomes a module of the world
  (`socket.socket` with `makefile()`, `create_connection()`, `create_server()` and the constants), `os.open()`, `os.read()`,
  `os.write()`, `os.close()`, `os.unlink()`, `os.remove()`, `os.fdopen()`, `open()` (also as `io.open()`, used by `pathlib`) and
  `time.sleep()` act on the world, and the failures raise the `OSError` of the `errno` (such as `ConnectionRefusedError`). The
  files given by `open()` are the usual buffered binary or text streams of `io`, on a raw stream calling the system calls of the
  world, writing `\n` as is even on Windows. `sys.stdout` and `sys.stderr` write on the standard streams of the world, line by
  line, while the uncaught exceptions still reach the PLM console (`sys.excepthook`). `Remote.py` imports the real socket module
  as `_socket` and writes its own messages on `sys.__stderr__` for that reason. The usual mistakes (`str` given to `send()`,
  malformed address) raise the exception of Python with a hint. The glue only exports `getParamString()` and `getParamInt()`,
  for the code of the entity.
* **The Java glue** (`RemotePosixGlue.java`, appended in the class of the generated methods, which are private and named
  `plm_remote_xxx`) offers nested classes with the interface of `java.net.Socket`, `java.net.ServerSocket` (with their
  streams), `java.net.DatagramSocket` (using the `DatagramPacket` of the JDK), of `Thread.sleep()`, of the file streams
  (`FileInputStream`, `FileOutputStream`, `FileReader`, `FileWriter`, and `PrintWriter` whose constructor taking a file name
  opens it in the world) and of the usual methods of `java.nio.file.Files`
  (`readString()`, `readAllBytes()`, `readAllLines()`, `writeString()`, `write()`, `delete()`, `deleteIfExists()`), which
  throw the exceptions of the JDK (such as `ConnectException` or `FileNotFoundException`). They are listed in
  `@Glue(replaces = ...)`: the generated entity imports them by name, which beats the imports on demand of its template
  (`java.net.*`) and the implicit `java.lang.*`, while its single-type imports of the replaced classes are dropped. The static
  initializer of the glue redirects `System.out` and `System.err` to the world, and the generated `Main` keeps the original
  `System.err` to print the uncaught exceptions on the PLM console. The leading `import` lines of a Java glue are moved before
  the generated class. As these templates use the classes of the glue, `lessons/network/**/*Entity.java` are not compiled with
  the PLM (see the `pom.xml`).
* **The Scala glue** (`RemotePosixGlue.scala`, appended in the object of the generated methods, private and named
  `plm_remote_xxx`) offers the same classes as the Java one, since Scala programs use those of the JDK, with the accessors of
  Scala (`socket.getInputStream`, without parentheses). The same `@Glue(replaces = ...)` makes the generated entity import them
  explicitly, which beats the wildcard imports (`java.net._`). It redirects `System.out` before the first use of `Console`,
  which keeps the `System.out` of that time for `println()`. The templates are written in Scala 3 with braces.
  `scala.io.Source.fromFile()` is not replaced, since `replaces` is shared with Java, which has no such class: the students
  read the files with the classes above.
* **The display**: `PosixWorldView` draws the student's machine and the peers' ones (mirrored), with the descriptors of their
  processes, the kernel objects in violet, their queues as cells, and the network in green. `PosixTracePanel`, under
  the view, traces the system calls in the style of strace (with the data cut after 50 characters, but the paths whole) and the
  end of the process (`+++ exited with 0 +++`, from `Entity.processEnded()` that `RemoteExecutionLang` calls), the ongoing steps
  of the peers, and their remaining steps greyed.
  A click on a file, on the box of a connected socket (showing everything it received and sent), of a bound datagram socket
  (showing each datagram it received or sent, with its address and its bytes as `hexdump -C` shows them), or on the `stdout`
  or `stderr` of the student's process (showing everything written on it), opens it in a read-only tab of the editor, which
  follows the changes of the world. This uses `MissionEditorTabs.showReadOnly(title, world, content)`
  (reached with `MainFrame.getInstance().getEditorTabs()`), which any universe can use: the tabs are `ReadOnlyTab`, listening
  to the world until the student closes them, or until the exercise or the language changes. Their title gives the name of the
  world (and "objective" for the expected one), and clicking again on a text shows its current content in the same tab.
* **The timeline**: the controls above `PosixWorldView` switch it to a timeline, drawing the successive states of the world one
  under the other, linked by arrows labelled by the event that led from one to the next. Each arrow hangs under the machine of
  the process that made the call (or between the machines for the network), and the machines that did not act are dimmed.
  The combo box shows either the system calls only, the transmissions of the network being merged into the next state shown
  (the last state is always shown), or all the events. A checkbox hides the standard streams, in both modes. These options are
  static, shared by all the views (such as the current world and the objective), and not saved between sessions.
  - The states come from `PosixWorld.history`: `log(actor, who, what)`, which adds every event to the trace, also keeps a
    `Scene` of the world after it, i.e. copies of the processes (the student's first, then the peers' ones, copied with a
    shared map so that the connections between them are kept) and of the files, with the index of the acting process (-1 for
    the network). The initial state is added by `reset()`, and the history stops after `MAX_SCENES` (1000) events, which the
    timeline then tells. A new kind of event must thus go through `log()` with its process, to appear in the timeline.
  - A change made without an event of the trace appears in the next state without an arrow of its own: for example, a scripted
    server starts listening when its script reaches `accept()`.
  - The timeline only draws the states that are visible, follows the end of the history during a run if it was shown, and does
    not open the editor on a click (only the current state does, its tabs following the world).
* **No world I/O yet**: the expected worlds are recomputed at each load.

# Maintainer's note

## Managing translations

Here are the commands to run to update the pot files on weblate, to
allow the translators to update their work. This should be done
regularly.

- po4a po4a.conf
- mvn -Pi18n-update -DskipTests process-classes (regenerates `l10n/engine/plm.pot`, see `PrimitivePot`; needs xgettext). A
  comment starting with `// Translator:` reaches the translators with its message, with the following lines of the same
  comment, if it is on the lines just before the one where the string starts (inside the parentheses of `Game.i18n.tr(` when
  the string goes to the next line, as clang-format may do). This update fails if a comment is lost
  (`l10n/check-translator-comments.sh`). When the code depends on a piece of a translated text (such as a URL that the
  programs of the students extract), such a comment can say `please keep this string unchanged (without the quotes): "..."`,
  which `TranslationsTest` then checks in every translation.
- git checkout l10n/*/*.po
- git commit -m "Update translation templates" l10n/*/*.pot
- git push && wlc pull

## Releasing the PLM

This is the check list to complete a new version of the PLM. It is
mostly for internal use.

Building the release:
- The content of weblate is correctly integrated.
  - wlc commit && wlc push && git pull --rebase
- All tests pass
  - ant test-all
- The mission texts are correctly translated:
  - po4a po4a.conf
  - Commit every translated file (eg, **/*.fr.html) in git
- ChangeLog
  - Ensure that all changes are documented
  - Update the release date and version number (even number for stable)
- Update the PLM_VERSION variable in .appveyor.yml to match the ChangeLog
  - Use an even number for the stable release.
- Update the version number in lib/resources/plm.configuration.properties
- Git: commit everything
  - git push && git tag v2.??.?? && git push tags

Publishing the release:
- Open the plm-src.jar, and repack it as a tgz file containing a directory
  - mv plm-src.2.9*.jar /tmp/ ; mkdir /tmp/plm-2.9.XXX; unzip ../plm-src.2.9* -d /tmp/plm-2.*
  - cd /tmp ; tar plm-2.9.XXX ; gzip -9v plm-2*.tar
- Document the tag on github, and then upload all 4 artefacts from appveyor
- Modify the web page to point to the latest release, and publish it
- Announce it on Discord and Tweeter

Publishing the Debian package:
- gbp import-orig plm-src.*.tgz
- dch -i "New upstream release."
- Edit debian/changelog to include [some ideas of the] upstream changelog
- git commit -m "Package the new upstream release" debian/changelog
  git-pbuilder update
  gbp build-package --git-pbuilder --git-tag
- Install and test the built package
- debsign ../build-area/plm_*-1_source.changes
  dput ../build-area/plm_*-1_source.changes

Preparing the next release cycle
- Create a new entry in Changelog with an odd patch version
- Update the version number in .appveyor.yml and plm.configuration.properties
