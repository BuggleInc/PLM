The XMPP protocol

The XMPP server of this world serves the domain buggleinc.lan (RFC 6120 and 6121), and its chat rooms on conference.buggleinc.lan (XEP-0045, Multi-User Chat). Its users are known by their address (a JID), written as user@buggleinc.lan. They authenticate with a password, then join the rooms and talk there with the other occupants.

Framing

Each direction of the connection carries a single XML document, called a stream: it starts with the opening tag <stream:stream ...> (after an optional XML declaration <?xml version='1.0'?>), and only ends with </stream:stream> when the connection ends. The messages are the elements directly inside this root element, called stanzas, such as <message>...</message>. There is no length before them, and no line end after them: a stanza ends where its first tag is closed, once the nesting of its elements gets back to the root. A stanza may contain elements with the same name as itself, such as a <message> quoted inside a message, so the first </message> found does not always end the stanza. An element without content may be written as a single tag, such as <success/>. Some spaces may come between two stanzas: the servers and the clients send a single space now and then to keep the connection alive. The network does not keep the limits of the stanzas either: a single recv() may return several stanzas, or only the beginning of one, cut anywhere, even in the middle of a tag.

The values of the attributes are quoted with ' or ", as each program likes. In the texts and the values, five characters are written as references: &lt; for <, &gt; for >, &amp; for &, &apos; for ' and &quot; for ". A text never holds a raw < nor &, and the receiver must decode the references to get the text. XMPP forbids the comments, the processing instructions (but the XML declaration) and the DTD. The texts of this server are in ASCII.

Opening the stream and authenticating

The client speaks first, with the header of its stream, which names the domain of the server, the namespace of the stanzas of a client, the prefix stream and the version of XMPP:
<stream:stream to='buggleinc.lan' xmlns='jabber:client' xmlns:stream='http://etherx.jabber.org/streams' version='1.0'>
The server answers with the header of its own stream (with an id), then with its features: here, the authentication mechanisms of SASL that it offers, only PLAIN.

With PLAIN (RFC 4616), the client sends its credentials in the element <auth xmlns='urn:ietf:params:xml:ns:xmpp-sasl' mechanism='PLAIN'>: a zero byte, the user name (without the domain), a zero byte and the password, all encoded in base64. The server answers <success xmlns='urn:ietf:params:xml:ns:xmpp-sasl'/>, or a <failure> holding the condition and a <text> explaining it, after which the client may try again.

not-authorizedThe user name or the password is wrong.
malformed-requestThe decoded credentials do not hold two zero bytes, or are empty.
incorrect-encodingThe content of <auth> is not in base64.
invalid-authzidThe credentials start with something else than a zero byte (or the address of the user).
invalid-mechanismThe mechanism is not PLAIN.

Once authenticated, the client may send its stanzas at once. RFC 6120 asks the client to restart the stream after the success, by sending a new header, which this server accepts: it then answers with a new header and empty features (<stream:features/>). The address of the client is then user@buggleinc.lan.

Chat rooms

A room has the address name@conference.buggleinc.lan, and each occupant the address of the room followed by its nickname, such as name@conference.buggleinc.lan/Alice. To join a room, the client sends its presence to its own address in the room: <presence to='name@conference.buggleinc.lan/nickname'><x xmlns='http://jabber.org/protocol/muc'/></presence>. The server then sends, in this order:

  • the presence of each other occupant, from its address in the room;
  • the presence of the client in the room, holding <status code='110'/> to tell that it is its own;
  • the history of the room: the last messages said before the client came, each with a <delay xmlns='urn:xmpp:delay'/> giving their time in its attribute stamp;
  • the subject of the room, in a message from the room itself, holding a <subject> but no body. It always comes last, and tells that the client is in the room.

The messages of the room then come as they are said: <message from='name@conference.buggleinc.lan/Alice' to='user@buggleinc.lan' type='groupchat'><body>the text</body></message>. A message may hold more elements than its <body>, such as its XHTML version (an <html> holding a <body> of its own, XEP-0071) or a message that it forwards (inside a <forwarded>, XEP-0297): its text is in the <body> directly inside the message.

To talk in the room, the client sends a message of type groupchat to the room: <message to='name@conference.buggleinc.lan' type='groupchat'><body>the text</body></message>. The room sends it to every occupant, the client included, which thus gets its own message back from its address in the room. As on IRC, a message for someone in particular starts with its nickname and a colon, such as Alice: hello!, and the other occupants may answer it. A private message goes to the address of an occupant, with the type chat, and its answers come with the type chat too. The client leaves a room by sending its presence of type unavailable there, which the room confirms.

Ending the stream

The client ends its stream with </stream:stream>. The server ends its own stream in turn and closes the connection.

Errors

A stanza that the server cannot deliver comes back as an error stanza of the same kind, of type error, from the address it was sent to (with its id, if it had one). It holds an <error> with its type, its condition and a text explaining it, such as <message from='lobby@conference.buggleinc.lan' to='user@buggleinc.lan' type='error'><error type='cancel'><item-not-found xmlns='urn:ietf:params:xml:ns:xmpp-stanzas'/><text xmlns='urn:ietf:params:xml:ns:xmpp-stanzas' xml:lang='en'>There is no room lobby on conference.buggleinc.lan.</text></error></message>. The stream goes on.

item-not-foundThe room or the occupant does not exist, or the address is not a room.
jid-malformedThe presence joining a room lacks the nickname.
conflictAnother occupant has that nickname.
not-acceptableThe client sends to a room that it did not join.
bad-requestThe type of the message is wrong: groupchat to a room, chat to an occupant.
service-unavailableA request <iq>, which this server does not answer.

A worse mistake ends the stream: the server sends a <stream:error> with the condition and a text explaining it, ends its stream and closes the connection, such as <stream:error><not-authorized xmlns='urn:ietf:params:xml:ns:xmpp-streams'/><text xmlns='urn:ietf:params:xml:ns:xmpp-streams' xml:lang='en'>The client must authenticate with &lt;auth&gt; before sending any stanza.</text></stream:error></stream:stream>.

not-well-formedThe XML is broken: an element closed by another name, a raw < or & in a text, a value without quotes, some text between the stanzas...
restricted-xmlA comment, a processing instruction or a DTD.
bad-formatThe stream does not start with its header.
host-unknownThe header does not name the domain buggleinc.lan.
invalid-namespaceThe header lacks xmlns='jabber:client' or the declaration of the prefix stream.
unsupported-versionThe header lacks version='1.0'.
not-authorizedA stanza sent before the authentication.
unsupported-stanza-typeAn unknown element in the stream, such as <auth> without its namespace.
policy-violationAn authentication when the client is already authenticated.

Example session

In this session, the user student has the password secret, and the room lobby has the subject "Say hello!" and Alice as only occupant, who speaks two seconds after the client joined. The lines starting with C: are sent by the client, and those starting with S: by the server. These prefixes and the line ends are not part of the data: each line is sent without anything between it and the next one.

C: <?xml version='1.0'?><stream:stream to='buggleinc.lan' xmlns='jabber:client' xmlns:stream='http://etherx.jabber.org/streams' version='1.0'>
S: <?xml version='1.0'?><stream:stream xmlns='jabber:client' xmlns:stream='http://etherx.jabber.org/streams' id='plm1' from='buggleinc.lan' version='1.0' xml:lang='en'>
S: <stream:features><mechanisms xmlns='urn:ietf:params:xml:ns:xmpp-sasl'><mechanism>PLAIN</mechanism></mechanisms></stream:features>
C: <auth xmlns='urn:ietf:params:xml:ns:xmpp-sasl' mechanism='PLAIN'>AHN0dWRlbnQAc2VjcmV0</auth>
S: <success xmlns='urn:ietf:params:xml:ns:xmpp-sasl'/>
C: <presence to='lobby@conference.buggleinc.lan/student'><x xmlns='http://jabber.org/protocol/muc'/></presence>
S: <presence from='lobby@conference.buggleinc.lan/Alice' to='student@buggleinc.lan'><x xmlns='http://jabber.org/protocol/muc#user'><item affiliation='member' role='participant'/></x></presence>
S: <presence from='lobby@conference.buggleinc.lan/student' to='student@buggleinc.lan'><x xmlns='http://jabber.org/protocol/muc#user'><item affiliation='none' role='participant'/><status code='110'/></x></presence>
S: <message from='lobby@conference.buggleinc.lan' to='student@buggleinc.lan' type='groupchat'><subject>Say hello!</subject></message>

C: <message to='lobby@conference.buggleinc.lan' type='groupchat'><body>Hello Alice &amp; all!</body></message>
S: <message from='lobby@conference.buggleinc.lan/student' to='student@buggleinc.lan' type='groupchat'><body>Hello Alice &amp; all!</body></message>
C: </stream:stream>
S: </stream:stream>

Realism of this server

This server behaves as the real ones in everything described above, but it is simpler on the following points. A client written for this world would mostly work on real servers, with some additions.

  • The connection is not encrypted: this server does not offer <starttls/> in its features. Most real servers require TLS before the authentication (with <required/> in this feature), and refuse PLAIN on a connection in clear text, where the password would travel readable by anyone.
  • The real servers offer stronger mechanisms than PLAIN, such as SCRAM-SHA-1 or SCRAM-SHA-256, which prove that the client knows the password without sending it.
  • After the restart of the stream, a real server offers to bind a resource (<bind/>), and only accepts the stanzas once the client asked for one with an <iq>: its address then becomes user@domain/resource, one per connection of the user. This server takes the address user@domain at once.
  • This server answers no <iq>: no roster (the list of contacts), no discovery of the services, no ping. The occupants of the rooms follow a script, and the rooms are neither created nor configured by the clients.
  • The messages carry no id unless the client gave one, nor the <stanza-id> of XEP-0359 that the real rooms add, and this server never sends a space alone unless the world asks for it.
  • A real server limits the size of the stanzas and the rate of the client, and closes the idle connections.
