The DNS protocol

The DNS server of this world follows the RFC 1035 as the usual servers. It is authoritative for one zone (all the names ending with buggleinc.lan): it answers the queries about these names, and does not ask the other servers about the other names. It listens on the UDP port 53.

Framing

Each message (query or answer) travels in a single UDP datagram: the client sends a query with sendto(), and receives the answer with recvfrom(). Over UDP, an answer has at most 512 bytes, so a buffer of 512 bytes is enough. The messages are binary: all the numbers are written in network byte order, the most significant byte first (1 is written 00 01 on two bytes, as htons() gives it).

A message is made of a header of 12 bytes, then of four sections: the questions, the answers, the authority records and the additional records. The header tells how many entries each section holds.

Header

BytesFieldContent
0-1IDChosen by the client, and copied in the answer, so that the client can match the answers with its queries.
2-3Flags16 bits, from the most significant one: QR (0 for a query, 1 for an answer), opcode on 4 bits (0 for a standard query), AA (the answer comes from an authoritative server), TC (the answer was truncated), RD (the client desires recursion), RA (the server does recursion), 3 bits set to 0, and the response code (RCODE) on 4 bits. A query usually has the flags 01 00 (only RD set).
4-5QDCOUNTThe number of questions: 1 in a query.
6-7ANCOUNTThe number of answer records (0 in a query).
8-9NSCOUNTThe number of authority records (0 in a query).
10-11ARCOUNTThe number of additional records (0 in a query).

Names

A name such as www.buggleinc.lan is made of labels separated by dots (www, buggleinc and lan). In a message, each label is written preceded by a byte giving its length (at most 63), and the name ends with a zero byte, which is the empty label of the root. The dots are not written: www.buggleinc.lan becomes the 19 bytes 03 "www" 09 "buggleinc" 03 "lan" 00, where "www" stands for the ASCII bytes of these letters. A name has at most 255 bytes, and the case of its letters does not matter.

Question

A question is a name, followed by its type on 2 bytes (the kind of record asked) and its class on 2 bytes (always 1, IN, for Internet). The types known by this server are:

TypeValueData of the record
A1An IPv4 address, on 4 bytes: 0a 00 00 01 for 10.0.0.1.
TXT16A free text, as one or several strings, each preceded by a byte giving its length.
SRV33Where to find a service (RFC 2782): its priority, its weight and its port on 2 bytes each, then the name of the target machine. The clients try the targets of lowest priority first, and among them, choose at random with a probability proportional to the weight.
ANY255Only in a question: asks for all the records of the name.

The name of a SRV record tells the service and its transport, with labels starting with an underscore: _service._proto.domain. For example, _imap._tcp.buggleinc.lan would give the IMAP server of the domain buggleinc.lan.

Records

Each record of the answer and additional sections is made of its name, its type (2 bytes), its class (2 bytes), its time to live in seconds (TTL, on 4 bytes, telling how long the clients may keep it in a cache), the length of its data (2 bytes), and its data, whose content depends on the type. The answer starts with a copy of the question of the query, before the records.

A name may be written in a shorter form in the answers of a real server, which this server never uses (see below): a compression pointer, on two bytes whose two highest bits are set, telling at which offset of the message the rest of the name was written before.

Answers of this server

Besides the answer section, the answers about a name hold its TXT records in their additional section, where the administrators of this zone leave notes. A datagram that is not a query (shorter than a header, or with the QR bit set) is ignored, as real servers do: the client then waits forever. Realism of this server

This server behaves as the real ones in everything described above, but it is simpler on the following points. A client written for this world would mostly work on real networks, with some adaptations.

  • The names of the answers are always written in full. The real servers compress them: a name already written in the message is replaced by a pointer of two bytes (c0 0c for the name of the question, at offset 12). A client reading the answers of a real server must follow these pointers, or it gets lost in the message.
  • The NXDOMAIN answers, and the NOERROR ones without records of the asked type, have no authority record. A real server adds the SOA record of its zone there, which tells how long the clients may keep this negative answer in a cache. Its zone also has SOA and NS records at its top, which this one does not have.
  • The additional section only holds the TXT records of the asked name. A real server rather puts there the addresses of the names given by its answers (such as the targets of the SRV records), to save the client another query, and never puts unrequested TXT records there.
  • The TXT records hold ASCII text. Real ones may hold any bytes, often UTF-8 text.
  • This server does not implement EDNS (RFC 6891), which lets the client announce a larger buffer with an additional OPT record, so that the answers may exceed 512 bytes. It ignores the additional records of the queries, while a real server without EDNS answers FORMERR to such queries. A longer answer is truncated (TC bit), and the client should then ask again over TCP, where each message is preceded by its length on two bytes, which this server does not offer.
  • A real server limits the rate of its answers to each client, and its queries usually come from a resolver (the one of the C library, or a server of the network) rather than from the applications themselves. Real clients also choose a random ID and a random source port for each query, and check them in the answer, to resist spoofed answers.
  • As any server answering everybody, it uses recvfrom() and sendto() on an unconnected socket. Its clients may either do the same, or connect() their socket to the server first and use send() and recv(), as the resolver of the GNU C library does: the server answers from the address on which it received the query, so both work.
