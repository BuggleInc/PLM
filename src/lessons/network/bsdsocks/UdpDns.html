DNS over UDP

Now that you know how to exchange datagrams, it is time to talk to the BuggleInc DNS server, which listens on the UDP port 53 of the machine 10.0.0.53. The URL given by Bob is not in the usual DNS: you have to talk to this server directly, by writing your queries yourself. Bob said to be careful: the DNS server may tell you more than what you ask, so pay attention to everything it sends back.

The DNS messages are binary: the numbers are written on several bytes, the most significant one first, and the names are not written as text. The world documentation (in the section The servers of this world) describes the format of the queries and of the answers, the kinds of records, and the meaning of the response codes. The trace of the world shows how the server understood each of your queries and what it answered, and explains why it rejects a malformed one.

[!c]

Here are the main tools to build and read binary messages in C.

  1. An array of unsigned char holds the bytes of a message. Use unsigned char rather than char, whose values above 127 are negative.
  2. uint16_t htons(uint16_t n) and uint16_t ntohs(uint16_t n) convert a number of 2 bytes between the byte order of your machine and the network byte order (htonl() and ntohl() do the same on 4 bytes). memcpy() copies such a number in the message, or out of it.
  3. sendto() sends exactly the number of bytes that you give, and recvfrom() returns the number of bytes received.
[/!] [!python]

Here are the main tools to build and read binary messages in Python.

  1. A message is a bytes value. bytes([3, 65]) builds bytes from their values, "text".encode("ascii") gives the bytes of a text, and + puts bytes one after the other. data[i] is the value of a byte, and data[i:j] the bytes from i to j (excluded).
  2. struct.pack("!HH", a, b) writes the numbers a and b on 2 bytes each, in network byte order ("!"). "I" stands for a number on 4 bytes. struct.unpack("!HH", data) reads them back, as a tuple.
[/!] [!java|scala]

Here are the main tools to build and read binary messages[!scala] in Scala, which uses the classes of Java[/!].

  1. A message is an array of byte. new ByteArrayOutputStream() collects bytes: write(b) adds one byte, writeBytes(array) adds an array, and toByteArray() gives the result. text.getBytes(StandardCharsets.US_ASCII) gives the bytes of a text.
  2. ByteBuffer.wrap(array) reads and writes numbers in an array, in network byte order: getShort(i) and putShort(i, n) on 2 bytes, getInt(i) and putInt(i, n) on 4 bytes, and get(i) for a single byte.
[/!]

What to do

Find the IP address of the XMPP server hosting the chat room given by Bob, and print it on the standard output (such as 10.0.0.1, followed by a new line), before closing your socket. Your program must work in both worlds: the BuggleInc zone is not exactly the same in each of them. While exploring, you will certainly print what the server answers, but your output is compared to the expected one: in the end, print only the address, and remove your other messages.

The first step is certainly to ask the TXT records of the name buggleinc.lan, where the administrators of the zone leave notes, and to read all the records of the answer. They will probably give you more hints, and so may the TXT records coming in the additional section of the next answers.

Additional hints

Accessing a DNS server directly on the wire is not an easy task, but don't worry. This exercise provides several hints to help you in this task. Some of these hints are given below, while others come with the answers of the server.

  • Please refer to the world's documentation for more info about the DNS wire protocol.

    Your TXT query should contain a 12-byte header, formatted as follows:

    1. 2 bytes representing the query ID. The server will reuse the exact same ID in its answer. Pick the value you want.
    2. 2 bytes representing the flags. 01 00 are the usual flags of a query: only RD (recursion desired) is set. The BuggleInc server never goes recursive, so this will be ignored.
    3. 2 bytes representing the number of questions in this message, in network byte order. 00 01 for one question.
    4. 2 bytes representing the number of answers in this message, in network byte order. 00 00 for zero answer.
    5. 2 bytes representing the number of authority records in this message, in network byte order. 00 00 for no such record.
    6. 2 bytes representing the number of additional records in this message, in network byte order. 00 00 for no such record.

    Then comes the question: the name about which you are looking for something, plus the code of the TXT type, plus the class IN (Internet).

    0x09 "buggleinc" 0x03 "lan"   # the name, each label prefixed by its length and encoded in ASCII
0x00                          # this zero ends the name
0x00 0x10                     # 0x00 0x10 in hexadecimal is 16 in decimal, which stands for TXT
0x00 0x01                     # 0x00 0x01 in hexadecimal is 1 in decimal, which stands for IN (Internet)

    In hexadecimal, the text between quotes standing for its ASCII bytes. The query thus has 31 bytes: 12 for the header, 12 ASCII chars for the name without the dots, 2 bytes for the length of each label, the final zero byte ending the name, and 2 bytes for the query type and 2 bytes for the Internet class.

    The answer starts with a header of 12 bytes as well: the same ID, the flags (whose last 4 bits are the response code, 0 when everything went well), and the numbers of questions, answers, authority records and additional records. For example, if your query had the ID 0x12 0x34:

    0x12 0x34  0x85 0x00                 # your ID, and the flags of an answer (response code 0: NOERROR)
0x00 0x01  0x00 0x01                 # 1 question and 1 answer...
0x00 0x00  0x00 0x00                 # ...but no authority nor additional record
0x09 "buggleinc" 0x03 "lan" 0x00     # the question, copied from your query: skip it
0x00 0x10  0x00 0x01
0x09 "buggleinc" 0x03 "lan" 0x00     # the answer record: its name,
0x00 0x10  0x00 0x01                 # its type (TXT) and its class (IN),
0x00 0x00 0x0e 0x10                  # its time to live (3600 seconds), that you can ignore,
0xLL 0xLL                            # the length of its data, on 2 bytes,
0xNN "..."                           # and its data: for a TXT record, the length of the text on 1 byte, then the text

    To read it, skip the header and the question (the name up to its zero byte, then 4 bytes), then read each record in turn: its name up to its zero byte, its type, its class, its time to live and the length of its data, and finally its data. The length of the data tells you where the next record starts. Make sure to inspect every record of the answer, in particular the TXT records in the additional records of the other answers.

    Your SRV query should contain a 12-byte header, formatted as follows:

    1. 2 bytes representing the query ID. The server will reuse the exact same ID in its answer. Pick the value you want.
    2. 2 bytes representing the flags. 01 00 are the usual flags of a query: only RD (recursion desired) is set. The BuggleInc server never goes recursive, so this will be ignored.
    3. 2 bytes representing the number of questions in this message, in network byte order. 00 01 for one question.
    4. 2 bytes representing the number of answers in this message, in network byte order. 00 00 for zero answer.
    5. 2 bytes representing the number of authority records in this message, in network byte order. 00 00 for no such record.
    6. 2 bytes representing the number of additional records in this message, in network byte order. 00 00 for no such record.

    Then comes the question: the name about which you are looking for something, plus the code of the SRV type, plus the class IN (Internet).

    0x03 "aze" 0x09 "buggleinc" 0x03 "com"   # the name, each label prefixed by its length and encoded in ASCII
0x00                                     # this zero ends the name
0x00 0x21                                # 0x00 0x21 in hexadecimal is 33 in decimal, which stands for SRV
0x00 0x01                                # 0x00 0x01 in hexadecimal is 1 in decimal, which stands for IN (Internet)

    In hexadecimal, the text between quotes standing for its ASCII bytes. The query thus has 35 bytes: 12 for the header, 15 ASCII chars for the name without the dots, 3 bytes for the length of each label, the final zero byte ending the name, and 2 bytes for the query type and 2 bytes for the Internet class.

    Make sure to inspect every record of the answer, in particular the TXT records in the additional records.

  • A SRV record is read as any other record (see the first hint): its name, its type, its class, its time to live and the length of its data, then its data. For example, here is a record of the answer to a SRV query on aze.buggleinc.lan:

    0x03 "aze" 0x09 "buggleinc" 0x03 "lan" 0x00            # the name of the record
0x00 0x21  0x00 0x01                                   # its type (SRV) and its class (IN)
0x00 0x00 0x0e 0x10                                    # its time to live (3600 seconds), that you can ignore
0x00 0x1a                                              # the length of its data: 26 bytes
0x00 0x0a                                              # the priority of the target: 10
0x00 0x05                                              # its weight: 5
0x10 0x92                                              # its port: 4242
0x04 "srv1" 0x09 "buggleinc" 0x03 "lan" 0x00           # its name, written as all the names

    The data holds 6 bytes of numbers, and 20 bytes of name. An answer may hold several such records, one after the other: the world documentation tells which target a client should use. Once you have the exact name of the host, you need another query to retrieve its IP address. Its IP address is what you need to write on your standard output to pass the exercise.

    The IP address of a machine is given by its A record. Your query starts with the same 12-byte header as the other queries (an ID of your choice, the flags 01 00, one question, and no other record), then comes the question: the name of the machine, plus the code of the A type, plus the class IN (Internet).

    0x03 "www" 0x09 "buggleinc" 0x03 "com"   # the name, each label prefixed by its length and encoded in ASCII
0x00                                     # this zero ends the name
0x00 0x01                                # 0x00 0x01 in hexadecimal is 1 in decimal, which stands for A
0x00 0x01                                # 0x00 0x01 in hexadecimal is 1 in decimal, which stands for IN (Internet)

    The query thus has 35 bytes, as the one of a name of the same length for any other type. In the answer, the data of an A record is 4 bytes long: these are the 4 numbers of the address, in order. The bytes 0x0a 0x00 0x00 0x2a stand for the address 10.0.0.42, each byte being printed in decimal, between 0 and 255.
