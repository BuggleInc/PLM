Framing messages: IRC

One of the biggest difficulties when exchanging data over the Internet is to determine whether all bits of an incoming message have been received already, or whether more data is incoming. Since the data travels over the network in packets, the data received so far could be only the first bits of the intended message, while the rest is still in transit. The only case where TCP tells you for sure that you received all emitted data is when the other side closes its socket, but this makes it difficult to pursue a dialog in several steps.

This problem is known as message framing. Since TCP does not provide any help here, solutions must be devised at the application level: the client and the server must agree beforehand on how to frame the different messages of their protocol. The easiest solution is indeed to close the socket once all data is sent, as we did in the previous exercises. This is also used in real protocols such as FTP (File Transfer Protocol), where the server opens a new connection each time it wants to send a file, and closes it once the whole file is sent. It works, but it is not very efficient because opening a new connection each time you want to send a piece of data takes time.

Another solution is to agree on a specific marker that can be used to separate the messages. The IRC protocol (used for instant messaging) decides for example that any message ends with the classical line ending markers, i.e. with the two chars \r\n, which are called CR for 'carriage return' and LF for 'line feed'. The SMTP and POP3 protocols (involved in mail exchanges) end the mail with a dot alone on its line (i.e. with the sequence of five chars \r\n.\r\n).

Extra difficulties may arise when the data can include the marker that was intended to mark the content end. When the user sends several lines in IRC, they are simply received as separate messages, leading to the line flooding that plagues IRC channels. But the mail server should not crash when receiving a mail in which a human wrote the \r\n.\r\n sequence on their own. This is why many protocols escape the markers when they are found in the input data. SMTP and POP3 double every dot starting a line in the input data (this mechanism is sometimes called "dot-stuffing"). Another protocol which would use '\n' as a marker could prefix every '\n' char of the input data with a backslash (the '\' char), and double every backslash of the input data. Reading the data from its start, the receiver then tells the markers from the '\n' of the data without any ambiguity. No backslash (or only escaped backslashes) preceed the '\n' markers.

Another classical solution to frame the messages is to prefix the message by its size. The DNS over TCP protocol for example sends the data size as a 16-bit integer (in network byte order) before the data itself. The receiver knows that it needs at least these two bytes of information, which then give the size of the complete message. On the other hand, this protocol does not allow messages that are larger than 65535 bytes.

HTTP is interesting with regard to message framing, because it uses several mechanisms together. Within each HTTP response (from the server to the client), a list of headers is separated from the data itself with two consecutive line ends (i.e. with the sequence \r\n\r\n). The list can be decomposed because each header field comes under the form header-name: header-value alone on its line. One of these headers is named Content-Length and its value is the size of the data, after the headers. So you have a framing between the header list and the data, another framing within that list and finally the data size is prefixed to the data itself.

The protocols serie

The protocols serie contains several exercises that will let you explore several classical protocols: IRC, DNS, XMPP, HTTP and finally FTP. In this first exercise you have to connect to an IRC server, join a channel, get an information from a (simulated) participant, disconnect from the server and display the information on your command line. The server you will connected to is a simulation that runs within the PLM, but it's realistic and implements the exact protocol of real servers on the Internet. You can find its documentation in the world documentation by pressing Ctrl-H.

To inspect the protocols, run your code step by step and clic on any socket or file descriptor to open the socket content in a new editor tab.

What to do

The IRC server listens on port 194 of the machine whose IP address is 10.0.0.1. You should first open a socket to that port, and display any information sent by the server. The greetings message will give you a hint of how to proceed.

The next step is to register to the server by sending a nickname with "NICK student", then your user name and your real name with "USER student 0 * :Your Name", each followed by the command delimiter \r\n. The server welcomes you with several lines, the first one starting with your nickname after the code 001, such as ":irc.example.org 001 student :Welcome to the network student". You can skip any line from the server that does not contain this 001 code, but you probably want to display these messages when your program fails to trigger a 001 from the server.

Once registered, join the #welcome channel on the server (see the world documentation for details on the join command). The server confirms with a line such as ":student!student@10.0.0.10 JOIN #welcome", then gives the list of the members of that channel in lines with the code 353, ended with a line with the code 366 such as ":irc.example.org 366 student #welcome :End of /NAMES list.", each line ending with the delimiter. The code 366 in a line says that you successfuly joined the channel and that the server is ready.

Once on the channel, you can wait a bit, displaying what the other (simulated) participants of the discussion have to say, but the exercise requests you to ask Bob about the treasure trove he keeps talking about. Send a message to Bob to know more, but please be polite: Bob is a bit grumpy, but he's a good guy. If you're stuck, more hints may come from the other people on the channel, so keep reading the conversation for more information.

Once you got the information from Bob, simply print the obtained URL to your standard output to not forget, and proceed to the next exercise.

Good luck!

Some help on framing messages in [!thelang]

The main technical difficulty is to get the framing right: you want a solution to get the lines received from the server one after the other, each with its \r\n separator. This is exactly the point of this exercise.

[!python]

A simple solution in Python is to write a little generator as follows. You should try to write it from this description before opening the hint that gives the complete code for that generator.

def lines(sock):
    buffer = b""
    while True:
        # if buffer already contains the b"\r\n" sequence --- test it using buffer.find()
           # split the buffer up to that sequence  -- split it using indices, e.g. buffer[:end] for the first half
           # remove the split part from the buffer -- using indices
           # yield the split part
        # in the other case (if the buffer does not contain the sequence)
          # receive up to 4096 bytes from the socket and append it to the buffer
          # if the socket got closed on the other side, deal with it
          # iterate in the loop to get a line

def lines(sock):
    buffer = b""
    while True:
        end = buffer.find(b"\r\n")
        if end >= 0:
            line, buffer = buffer[:end], buffer[end + 2:]
            yield line
        else:
            data = sock.recv(4096)
            if not data:             # end of the stream
                return
            buffer += data

Once you have the generator, your code can use it as follows.

reader = lines(sock)
data = next(reader)                        # the next line encoded as binary buffer (ie b"" ...), or the value StopIteration at the end
line = next(reader).decode("ascii") # the next line encoded as a sstring, or StopIteration at the end
data = next(reader, None)              # None at the end of the stream instead of an exception

Beware! this generator does not give strings but binary buffers. You can either encode your strings with b"some content" before searching the string in the received data, or decode the data with data.decode("ascii") before searching the strings in it.

[/!] [!c]

A simple solution in C is to use the fgets() function, that fills the provided buffer up to the next '\n' in the input stream and adds the '\0' after the last received char. The only thing is that this function takes a FILE* so you should first use fdopen() to build it from the socket that connect() gives. Usually, fgets() is annoying because it fails if the used buffer is too small, but this is not a problem with IRC, where messages are limited to 512 chars. A buffer of 513 chars will thus never overflow. Refer to the manpages of these two functions for more information.

FILE* in = fdopen(sock, "r");
char line[513];                                    /* 512 bytes of IRC, plus the final \0 */
while (fgets(line, sizeof line, in) != NULL) {     /* NULL at the end of the stream */
 ...
}

Some of the following functions may reveal useful, even if you don't need all of them.

  • char* strstr(const char* haystack, const char* needle): returns the first occurence of the substring needle in the string haystack, or NULL if the substring is not part of the string.
  • char* strchr(const char* str, int c): returns the first occurence of the char c in the string str.
  • char* strrchr(const char* str, int c): returns the last occurence of the char c in the string str.
  • char* strtok(char* str, const char* delim): tokenize the string around the provided delimiters. This is useful to split a string on spaces, if you need it. Check the manpage for details and for an example of use.
[/!] [!java|scala]

The easiest solution in [!thelang] is to build a BufferedReader in from the socket and then use in.readLine() to get the next line, or null if the socket was closed on the other side. String.contains(), String.indexOf(), String.lastIndexOf() and String.substring() are then useful to parse the server answers.

[!java]Socket socket = new Socket("10.0.0.1", 194);
BufferedReader in = new BufferedReader(new InputStreamReader(socket.getInputStream(), StandardCharsets.UTF_8));
OutputStream out  = socket.getOutputStream();

String line;
while ((line = in.readLine()) != null) {      // without its \r\n
  System.out.println(line);
}
socket.close();                              // closes the streams too
[/!][!scala]val socket = new Socket("10.0.0.1", 194)
val in     = new BufferedReader(new InputStreamReader(socket.getInputStream, StandardCharsets.UTF_8))
val out    = socket.getOutputStream

var line = in.readLine()
while (line != null) {                       // without its \r\n
  println(line)
  line = in.readLine()
}
socket.close()                               // closes the streams too
